# SEO-аудит под Яндекс

Методология перенесена из OpenSEO `seo-audit` (разбор — `docs/open_seo_review.md`) и переложена на наш стек. Исследуем широко, рекомендуем выборочно: в отчёт попадают **1–3 рекомендации**, которые либо забирают ощутимо больше целевого спроса, либо останавливают реальную потерю.

`PHP=/opt/homebrew/bin/php`; все команды — с `--no-debug`. Рабочая папка: `var/seo/audit/<домен>-<YYYY-MM-DD>/` (`var/` в .gitignore — клиентские данные в git не попадают).

## Режимы

| | **wearbase.ru** | **Клиентский домен** («Конвейер», диагностика 15 000 ₽) |
|---|---|---|
| Позиции | Вебмастер из БД (`yandex_query_stats`) — реальные, бесплатные | только живой SERP (`app:seo:serp`) или доступ клиента к Вебмастеру |
| Запрос → страница | `yandex_query_page`, `gsc_query_page` | вручную: SERP + чтение страниц |
| Здоровье | `yandex_site_health` (ИКС, исключённые, проблемы) | обход `tech-audit` |
| Отчёт | одна версия | **две версии** (см. «Выдача») |

Нет доступа к Вебмастеру/GSC клиента — это **пробел покрытия**, его пишем в отчёт, но аудит не блокируем. Первым письмом попросить клиента добавить нас представителем в Вебмастере: это заменяет платный SERP.

## Инструменты

- **Спрос**: `$PHP bin/console app:seo:wordstat "<фраза>" --limit=50 --json --no-debug`. Частотность по всей России (регион 225) — для регионального бизнеса это ограничение, пишем его в отчёт. ⚠️ Квота 100 запросов/час общая с `app:brand:keywords` → бюджет аудита **15–20 вызовов**. `status: UNKNOWN` значит «не измерено», а не «спроса нет».
- **Выдача**: `$PHP bin/console app:seo:serp "<запрос>" --domain=<домен> --limit=20 --json --no-debug`. Платный API (~0.49 ₽/запрос, дневной кап). Статусы:
  - `FOUND` — позиция = место первого URL домена; рядом `distinct_domains_above` (FLAT-группировка может занижать место — в отчёт пишем оба числа);
  - `NOT_IN_TOP` — выдача пришла, домена нет → «не в первых N»;
  - `UNKNOWN` — пустой ответ (ключ, кап, 4xx, сеть). **Никогда не превращать UNKNOWN в «не ранжируется».**
  - Регион — дефолт API: явный регион клиент не передаёт, локальную выдачу этим не измерить.
  - ⚠️ **Позиции API не откалиброваны** (на 2026-10-08 ключ Search API не работает). При первом живом прогоне взять 3–5 запросов wearbase с известной `position` из последнего `date_to` в `yandex_query_stats`, сравнить с `app:seo:serp --domain=wearbase.ru` и записать сюда, насколько они расходятся. До этого позиции SERP в клиентском отчёте помечать «оценка API, не откалибровано».
- **Обход сайта**: `$PHP -d memory_limit=512M bin/console app:seo:tech-audit --base=https://<домен> --stdout-only --json --limit=150 --no-debug | sed -n '/^{/,/^}/p' > tech.json`. Перед JSON в stdout идёт прогресс — `sed` вырезает только объект `{base, crawled, findings[{rule,…}]}`. Проверено на trim-ai.ru 2026-10-08: обход работает, в БД ничего не пишет.
  - ⛔ **Для чужого домена `--stdout-only` обязателен, `--notify` запрещён**: без него findings клиента запишутся в `seo_tech_finding`, а находки wearbase пометятся исправленными.
  - На чужом сайте все страницы считаются хабами (регэксп карточек — wearbase-специфичный), обход режется `--hub-limit`. Если сирот пропустили из-за лимита — так и пишем.
- **Позиции и разрывы wearbase**: `$PHP bin/console app:seo:gap-report --source=both --stdout-only --json --no-debug`. Дальше — SQL одной строкой через `dbal:run-sql`: `yandex_query_stats` (query_text, shows, clicks, position, date_to — брать последний `date_to`), `yandex_query_page` (query → page_url), `yandex_site_health` (последний `captured_on`).
- **Чтение страниц и конкурентов**: WebFetch/curl по сайту, sitemap.xml, robots.txt и по лидерам выдачи.

## Ход работы

### 1. Ориентация
1. Определить режим и бизнес: чем занимается сайт и кто его покупатель. Неясно — один вопрос пользователю.
2. Проверить, жив ли поиск: один `app:seo:serp` по брендовому запросу. Вернулся UNKNOWN → все позиционные утверждения для клиента идут как пробел покрытия. Сказать об этом пользователю сразу, а не в конце.
3. Запустить `tech-audit` (в фоне, `run_in_background`). Параллельно прочитать sitemap и навигацию и выписать **семейства страниц**: категории, карточки, услуги, гео, статьи, сравнения — то, что реально есть на сайте.
4. Сайт не открывается или почти пуст (сертификат, 5xx, одна страница) — сначала разобраться: редиректы, варианты www/https, поиск по имени бизнеса. Мёртвый домен с живым преемником переворачивает весь вывод.

### 2. Исследование каждого семейства, важного для цели
- Прочитать **≥2 страницы** семейства (основной контент, без шаблона): лучшую по данным и типичную или худшую. Вопрос к каждой: какое решение принимает тот, кто ищет, и даёт ли страница конкретный, проверяемый ответ — или подставляет город/название в общий шаблон? Сравнить с тем, что дают лидеры выдачи.
- Для каждой страницы, которую можем назвать в отчёте, проверить: код ответа, canonical, noindex/robots, как на неё попадают внутренними ссылками.
- Неровная видимость у соседних страниц одного семейства — разобрать причину (интент, конкретика, ссылки). Соседа, который уже в топе, защищаем, а не переписываем.
- Живые проверки делаются **сейчас**, а не после черновика: кластер запросов кандидата (головной + варианты, которыми реально ищут). Запросы, на которых держится главная рекомендация, перепроверить перед написанием. Две проверки расходятся — писать позднюю, раннюю в скобках («#7 (первая проверка: не в топ-20)»): это разброс одного дня, а не тренд.

### 3. Шорт-лист до решения
`opportunities.md` в рабочей папке: 5–10 кандидатов, **минимум трёх типов**:
- существующая страница недобирает спрос, под который сделана;
- есть спрос (Wordstat), но нет страницы, которая на него отвечает;
- страница-лидер, которую надо защитить или поправить;
- техническая потеря (индексация, дубли, каннибализация, редиректы).

На каждого кандидата: спрос (фраза, показов/мес, дата), текущая позиция со статусом, URL, гипотеза причины, цена вопроса (сколько переходов теряем), трудоёмкость. Отбор в отчёт — по произведению «спрос × достижимость», а не по числу найденных проблем.

### 4. Выдача
**wearbase.ru**: один отчёт `report.md` — вывод первым абзацем, 1–3 рекомендации, приложение с доказательствами. Новые выводы — в `docs/` по правилу фиксации знаний.

**Клиент** — две версии. Подробный бесплатный аудит = готовое ТЗ, которое клиент скормит своему агенту, поэтому даром отдаём только находки:
- `client.md` (бесплатная, можно отдавать): что сломано, масштаб, чем это обходится (цена вопроса в переходах или деньгах), блоки работ со сроками. **Без** перечней URL, карты «запрос → страница», ядра и пошагового плана — иначе клиент отдаст это ТЗ своему агенту.
- `full.md` (только после оплаты диагностики 15 000 ₽): перечни URL, карта «запрос → страница», ядро с частотностью и интентом, план по приоритетам. Дальнейшие работы — по сетке «Конвейера»: фундамент/ядро 60–90 000 ₽, страница под коммерческий интент 6 500 ₽, сопровождение от 55 000 ₽/мес (ниже не идём), GEO +20 000 ₽/мес; скидок знакомым не даём.

**Приложение с доказательствами** (в обеих версиях — в объёме, который версия допускает): для каждой позиции — запрос, дата и время, источник (Вебмастер или SERP API), сколько результатов вернулось, статус, найденный URL; для спроса — фраза, регион, дата. Пробелы покрытия перечислить явно: нет SERP, нет Вебмастера, частотность только по России, регион выдачи по умолчанию.

### Чего не делать
- Не выдавать оценки за замеры: позиция из одного снимка — не базовая линия.
- Не рекомендовать то, что не проверено живьём в этом аудите (результатам из БД старше 30 дней — только как ориентир).
- Не раздувать отчёт: 15 находок без приоритета хуже трёх с ценой вопроса.

В ответе пользователю (≤4000 символов): вывод, 1–3 рекомендации, пробелы покрытия, пути к файлам.
