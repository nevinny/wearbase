Риг = тот же хост, что и LLM-сервер (`ssh llm`, IP непостоянен — если хост недоступен, сначала скилл `llm-server`). Всё управление — через веб-дашборд `~/miner/dashboard.py` (:8088, только stdlib), майнер живёт в tmux-сессии **`mine`**, монета берётся из `~/miner/coins.json` (`active`). Реестр монет и UI — память `mining-dashboard-coin-registry`.

## Запуск

1. **Проверить, что уже крутится** (иначе поднимешь второй экземпляр):
   ```bash
   ssh llm 'tmux has-session -t mine 2>/dev/null && echo "майнер: жив"; pgrep -f "python3 dashboard.py" >/dev/null && echo "дашборд: жив"; curl -s -m 5 -o /dev/null -w "dash HTTP %{http_code}\n" http://127.0.0.1:8088/'
   ```
2. **Дашборд не поднят** — поднять (сам майнинг он НЕ стартует, автозапуска в коде нет):
   ```bash
   ssh llm 'cd ~/miner && setsid python3 dashboard.py >> dash.log 2>&1 </dev/null & exit 0'
   ```
   ⚠️ ssh-сессия всё равно может провисеть до таймаута Bash-инструмента (потомок держит канал) — **это не ошибка**: дашборд уже поднят, просто проверь следующим вызовом, а зависший таск сними. `nohup … &` без `setsid` виснет гарантированно.
3. **Майнера нет** — стартовать явно (идемпотентно, если уже крутится — вернёт `already running`):
   ```bash
   ssh llm 'curl -s -m 10 -X POST http://127.0.0.1:8088/start'
   ```
4. **Проверить, что шары идут** (через ~1 мин):
   ```bash
   ssh llm 'tail -c 1200 ~/miner/wildrig.log | tr -d "\r" | tail -14'
   ssh llm 'curl -s -m 5 http://127.0.0.1:8088/data'
   ```
   Ориентир для pearlhash на 4 картах: **~155 TH/s @ ~555 W** с применёнными power-лимитами, **~175 TH/s @ ~655 W** без них. Для BTX (srbminer) — ~14 kH/s, лог `~/miner/srb.log`.

## Автозапуск после ребута

- **Дашборд + майнинг**: user-юнит `rig-dashboard.service` (`~/.config/systemd/user/`, `enabled`, linger включён) — поднимает `dashboard.py` с `AUTOSTART_MINING=1`, тот через 15 с стартует активную монету (до 5 попыток: драйвер после ребута готов не сразу). Управление: `systemctl --user {status,restart} rig-dashboard`. **Правку dashboard.py применять через `systemctl --user restart rig-dashboard`**, не ручным `setsid` — иначе поднимутся два экземпляра на один порт.
  ⚠️ В юните обязателен **`KillMode=process`**: tmux-сервер майнера — потомок дашборда и лежит в его cgroup, при дефолтном `control-group` рестарт юнита убивает майнинг вместе с дашбордом.
- **Power-лимиты + fanctl**: root-юнит `rig-gpu-tune.service` (лимиты в `ExecStartPre`, fanctl демоном). **Поставлен и `enabled` с 2026-09-03** — после ребута поднимается сам, ручной бутстрап больше не нужен. Проверка: `systemctl is-active rig-gpu-tune`. Если не `active` — переставить (см. ниже), иначе карты на дефолтном TDP и драйверной кривой.

## Если бутстрап GPU слетел (нужен пароль sudo)

Штатно юнит уже стоит. Если он пропал, `sudo -n` на риге **не проходит** — сам не сделаешь. Отдать пользователю строкой для `!` (юнит-файл уже подготовлен):

```
! ssh -t llm 'sudo install -m644 ~/miner/rig-gpu-tune.service /etc/systemd/system/ && sudo systemctl daemon-reload && sudo systemctl enable --now rig-gpu-tune && systemctl --no-pager status rig-gpu-tune | head -12'
```

Разовая альтернатива без юнита (до следующего ребута):

```
! ssh -t llm 'sudo nvidia-smi -pm 1; for p in 0:140 1:140 2:140 3:135; do sudo nvidia-smi -i ${p%%:*} -rgc; sudo nvidia-smi -i ${p%%:*} -pl ${p##*:}; done; sudo pkill -f "fanctl.py auto"; sudo setsid python3 ~/miner/fanctl.py auto >> ~/miner/fan-daemon.log 2>&1 </dev/null & exit 0'
```

Пока это не сделано — карты на дефолтном TDP (2060S 184 W вместо 140, A4000 140 вместо 135) и на драйверной авто-кривой, которая **не раскручивает вентилятор A4000 выше ~77% даже при 91 °C** → карта дросселит до ~1110 МГц и теряет ~10% хешрейта. Не авария (wildrig стоит с `--gpu-temp-limit 93 / resume 87`), но замеры версий/тюнинга в таком состоянии недостоверны — сказать об этом явно.

## Вентиляторы: аппаратный floor — тише не сделать

⚠️ **Не пытаться приглушить карты на простое — это уже проверено замерами 2026-09-03 и упирается в прошивку.** Пол оборотов у каждой карты свой, ниже него драйвер команду клампит:

| GPU | Плата | VBIOS | min по NVML | Поведение |
|---|---|---|---|---|
| 0 | 2060S, sub_device `0xC7571462` | 90.06.4C.00.**7A** | 41% | слушается, но ниже 41% не идёт |
| 1 | та же плата | 90.06.4C.00.**65** | 29% | **не реагирует вообще** — 0% и при `set 0`, и при `set 90` |
| 2 | та же плата | 90.06.4C.00.**7A** | 41% | слушается, но ниже 41% не идёт |
| 3 | RTX A4000 | 94.04.57.00.08 | 30% | слушается; демон держит 30% против 41% у драйвера |

Тупики, которые **не надо проходить заново**:
- Правка `CURVE` в `fanctl.py` на `(35, 0)` — упирается в тот же кламп 41%. Уже пробовали, не работает.
- Драйверный zero-RPM «если снять демон и подождать» — 3.5 минуты без демона: GPU0/GPU2 стояли 42–43%, в ноль не сорвались. `min` в NVML одинаков в manual и в auto → это прошивка, а не режим.
- Корпусные PWM — каналов нет (`/sys/class/hwmon/*/pwm*` пусто, lm-sensors не стоит, `fancontrol` inactive).

Прежде чем объяснять «настройки не применяются», сделать positive control: `sudo python3 ~/miner/fanctl.py set 90` — GPU0/2/3 отзываются мгновенно и слышно на слух. Вернуть: перезапуск `rig-gpu-tune`.

По шуму тюнинг даёт выигрыш только на A4000 (30% вместо 41%); держать юнит стоит ради лимитов и кривой под нагрузкой.

**Открытые вопросы по железу** (софтом не решаются, только с разрешения владельца):
- **Вентилятор GPU1** — 0% при любой команде, при этом карта греется под ollama. Похоже на отключённый/умерший; нужен физический осмотр.
- **Тишина GPU0/GPU2** — только перешивка VBIOS `…7A` → `…65` (борд и sub_device идентичны GPU1). Нужен `nvflash` (на риге нет), дамп обеих прошивок в бэкап, сверка вендора памяти (ревизии 2060S различаются Samsung/Micron — кросс-флеш между ними ловит нестабильность). Необратимо.

Скрипт `~/miner/mine-wildrig.sh` — legacy (сессия `pearlw`, дублирует майнер мимо дашборда). Запускать его **нельзя**, брать оттуда только бутстрап лимитов/вентиляторов.

## Обновление WildRig

В дашборде кнопка **⭳ WildRig <версия>** (жёлтая, если на GitHub есть свежее) и эндпоинт:

```bash
ssh llm 'curl -s -m 400 -X POST http://127.0.0.1:8088/update'
```

Что делает: тянет последний релиз `andru-kun/wildrig-multi` (linux-архив) → проверяет, что новый бинарь отвечает `--version` → **останавливает майнер** (иначе ETXTBSY) → кладёт бэкап `~/miner/wildrig-multi.bak-<стараяВерсия>` → подменяет бинарь → поднимает майнер, если он работал. Проверка релиза кешируется на 6 ч (фоновый поток), в `/data` — блок `update{current,latest,available}`.

**Авто-откат встроен**: после подмены ждём 20 с и проверяем, что майнер жив. Если новая версия упала — лог сохраняется в `~/miner/wildrig-fail-<ver>.log`, бинарь возвращается из бэкапа, майнинг поднимается. Ответ вида «X не завелась (…) — откатил на Y, майнинг идёт» = риг работает, разбираться можно спокойно.

- **Ручной откат**: `ssh llm 'curl -s -X POST http://127.0.0.1:8088/stop; cp ~/miner/wildrig-multi.bak-<ver> ~/miner/wildrig-multi; curl -s -X POST http://127.0.0.1:8088/start'`.
- 🛑 **Решено 27.07.2026: остаёмся на 0.48.9, не обновляться.** 0.49.x не влезает в VRAM, пока в картах резидентна `gemma4:26b` (`Error out of memory ... Ap buffer` → `Failed to start OpenCL threads`; `--gpu-intensity` не спасает). Выигрыш 0.49.6 — только на A4000 (+7%, по ригу ~2%) и не окупает выселение LLM-стека. Если кнопку всё же нажали и версия не завелась — авто-откат уже вернул 0.48.9, просто не жать снова.
- Порядок при ручных перезапусках: **сначала модель, потом майнер** — он подстроит интенсивность под остаток VRAM (A4000 берёт intensity 1). Обратный порядок = ollama не влезет.
- После обновления сравнить TH/s с прежними: замер честен **только при одинаковом VRAM** — свободные карты сами по себе поднимают авто-интенсивность (A4000 с gemma в памяти получала intensity 1 вместо 8).
- SRBMiner так не обновляется (его путь версионный, `SRB_BIN` в `dashboard.py`) — руками.
- Правки самого `dashboard.py`: редактировать локальной копией (`scp` туда-обратно), бэкап `dashboard.py.bak-<дата>`, перезапуск — только `systemctl --user restart rig-dashboard` (см. «Автозапуск после ребута» выше). Рестарт дашборда майнинг не трогает (разные процессы, `KillMode=process`). Пользователю сказать перезагрузить вкладку — старая JS не знает новых кнопок.

## Остановка / переключение монеты

- Стоп: `ssh llm 'curl -s -m 10 -X POST http://127.0.0.1:8088/stop'` (убивает tmux `mine`; дашборд остаётся).
- Смена монеты: `POST /switch` c `coin=<id>` из `coins.json` — убьёт сессию и поднимет новую, sudo не нужен.
- Заведение монеты/кошелька — через UI дашборда (`✎ Монеты`) или `POST /coins`.

## Грабли

- ⚠️ Локальный `pkill -f "dashboard.py"` по ssh **убивает сам ssh-шелл** (строка в его argv) — гасить только по конкретному PID.
- Майнинг забирает GPU под 100% — **ollama/RAG-генерация встанет в очередь**. Перед долгим батчем конвейера (`app:brand:generate-content`, embed) майнинг лучше остановить, после — вернуть. Если пользователь одновременно жалуется на «медленную генерацию» и просит майнить — назвать конфликт, не решать молча.
- «0 шар» первые ~30–60 с — норма (коннект + первый job), не перезапускать.

Ответ — ОДНИМ сообщением: первым абзацем факт (запущено/остановлено + хешрейт и потребление), затем что осталось руками (бутстрап sudo, если после ребута).
