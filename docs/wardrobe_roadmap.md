# «Мой гардероб» → семейная гардеробная система: видение и роадмап

Дата: 2026-07-11, обновлено 2026-08-08. Источник: владелец продукта (запрос супруги как первого пользователя →
стратегическая продуктовая ставка).

## Ключевая идея

**Гардероб для всей семьи** — сильная продуктовая гипотеза differentiator: семья из 5+ детей —
идеальный сценарий, где вещи живут дольше одного носителя. Отсутствие сопоставимого семейного
контура у Whering, Indyx, Acloset и других аналогов нужно подтвердить отдельным конкурентным
исследованием; ценность — интервью, activation семьи, передачи вещей и retention family vs solo.

Синергия с WEARBASE-каталогом: вещи → ссылки на бренды каталога, вишлисты → трафик
брендам, AI-стилист → работает на данных RAG-конвейера брендов.

## Extension points, заложенные в фундамент итерации 3

- `Family` — первоклассная сущность (к ней цепляются бюджеты и вишлисты итерации 4).
- `wear_status` — расширяемое строковое поле (вишлист/awaiting_approval — кандидаты
  на отдельную сущность, решается в итерации 4).
- `WardrobeItem` готов к AI-атрибутам (цвет/сезон/стиль) и связям item↔item (итерация 5) —
  отдельными таблицами, схему менять не потребуется.
- `source` уже есть (web|telegram|import) — добавится mobile.

## Авто-ингест из фото (апгрейд ит. 1–2) — ✅ v2 2026-08-24

**Онбординг v2:** `/account/wardrobe-app` теперь начинает не с пустого каталога, а с короткой
activation-петли: выбрать свой или доступный детский профиль → добавить первые 5 вещей пачкой →
проверить AI-черновики → собрать первый образ → оставить реакцию. Состояние принадлежит владельцу
гардероба, сохраняет активную пачку и поддерживает «Пропустить/Продолжить» после нового входа.
Родитель загружает вещи именно ребёнку; `actor` и `profileSubject` фиксируются раздельно.

Принятие черновика идемпотентно: повторный запрос возвращает ту же вещь, а receipt остаётся связан
с `WardrobeItem`. Новые фото вещей и черновиков хранятся вне web-root и выдаются только через
family-aware `/account/wardrobe/media/*` с `private, no-store`; старые файлы читаются контроллером
в переходный период, прямой Apache-доступ к legacy-каталогам закрыт.

**Надёжность v2.1:** повторная загрузка тех же байтов определяется по SHA-256 до создания draft;
на пользователя действует отдельный upload rate limit. Worker атомарно забирает записи через
DB lease (`processing`, `workerId`, `leaseUntil`, `attempts`), возвращает временные сбои в очередь
и после трёх попыток показывает управляемую ошибку. В `ai_raw` сохраняется только минимальная
диагностика модели/confidence, без полного ответа vision-провайдера.

**Реализовано (v1):** сущность-staging `WardrobeItemDraft` (отдельная таблица, не трогает
`WardrobeItem`), multi-upload `/account/wardrobe/ingest/upload` (dropzone) → pending-черновики →
фоновая команда `app:wardrobe:ingest-drafts` (в `scheduled_command`, каждые 2 мин, распознаёт
через `WardrobeAiService::suggestFromPhoto`) → страница ревью с поллингом и confidence-гейтом →
accept промоутит в `WardrobeItem` (`source=import`), reject — hard-delete. HEIC режется на
аплоаде; EXIF-автоповорот + downscale в `LlmService`. Тесты: `WardrobeIngestControllerTest`
(6/6) + исторический E2E команды на живой gemma4. **Deferred:** дедуп (`possible_duplicates`),
`observed.{}`/bbox, отдельная целевая vision-модель и адаптер её удалённого вызова.

Источник рецепта: gist tandpfun `b73063c8be8fc46644da9925d48b3240` — «extract clothing»
skill (пайплайн распознавания гардероба из фото). Твит подаёт его как AI-стилиста,
но по факту это **ingest-половина**: превращает свалку семейных фото в структурный
гардероб. Генерации новых образов там нет.

**Задача:** рядом с ручным вводом карточек (веб + TG-шаблон) добавить путь
«загрузи пачку фото → авто-распознавание вещей → черновики карточек на подтверждение».
Снимает главный барьер онбординга: никто не занесёт 200 вещей руками.

Пайплайн (адаптация 9 шагов гиста под наш стек):
1. Нормализация фото (EXIF-ориентация, RGB, quality 95+).
2. Vision-распознавание надетых вещей → структурный манифест. Целевая локальная vision-модель
   будет поднята на том же домашнем сервере; точное имя — TBD и задаётся через
   `WARDROBE_VISION_MODEL`. Исторически `gemma4:26b` успешно прошла vision-E2E 2026-07-15,
   но теперь остаётся генератором/fallback, а не зафиксированной целевой vision-моделью.
   Удалённый vision-вызов через `llmq.php` пока не считается готовым: нужно подтвердить поддержку
   images в воркере или сделать адаптер; production endpoint определяется отдельно.
   ⚠️ NB: vision делит одну GPU (concurrency=1) с RAG/соц-генерацией —
   команда распознаёт серийно (`--limit`), задействует риг только на всплесках онбординга.
3. Дедупликация — **консервативная, только по фото-доказательствам**, авто-удаления
   по похожести генераций нет (семейный сценарий: тысячи фото, 5+ детей → один
   центральный проход на identity/дедуп, распознавание можно батчить).
4. Черновики карточек `WardrobeItem` (status=draft) → пользователь подтверждает.

**Маппинг manifest гиста → `WardrobeItem`** (ложится почти 1:1, наполняет и ит. 5):

| manifest (gist) | WardrobeItem | примечание |
|---|---|---|
| `category` | категория вещи | tops/bottoms/outerwear/footwear/accessories |
| `observed.{color,material,silhouette,construction}` | AI-атрибуты (ит. 5) | ровно те extension points — цвет/сезон/стиль отдельными таблицами |
| `confidence` (high/med/low) | флаг черновика | low → обязательное подтверждение |
| `graphic_policy` (exact/mark-only/omit) | политика лого/принта | против ложного бренда в матчинге вещь↔каталог |
| `source_refs[].bbox` | кроп-превью карточки | нормализованный `[l,t,r,b]` 0–1; исходный кроп как визуал, вырез на хромакее НЕ рендерим |
| `possible_duplicates` | подсказка дедупа | не авто-мёрдж |

**Принцип «omission over invention»** (из гиста) — переносим жёстко: не выдумывать
логотип/карман/бренд/материал, если не видно на фото. Ложный атрибут = мусор в
матчинге вещь↔бренд каталога.

## Технические заметки

- AI-фичи (ит. 5) гонять на домашнем LLM-сервере (gemma4:26b + отдельная vision-модель TBD + qwen3-embedding):
  сочетаемость = эмбеддинги атрибутов вещей + LLM-судья; капсулы/образы = генерация
  по структурированному гардеробу. Отдельный внешний API не нужен.
- Бюджетирование (ит. 4): цены уже в RUB (конвенция проекта), статистика трат по
  носителю есть с итерации 1; исходный покупатель фиксируется историей передач (ит. 3).
- Покупка, примерка, распознавание образа и учёт носок: полный продуктовый флоу,
  privacy-инварианты и фазы реализации — [family_purchase_learning.md](family_purchase_learning.md).
- Детские аккаунты без email — см. дизайн итерации 3 (механика claim при взрослении).
