Зафиксировано 06.06.2026. Обе — для брендов с тонким/JS-сайтом и для усиления RU-discover.

## Ветка A: Яндекс в discover через XMLRiver (ПАУЗА)

**Проблема:** Яндекс отдаёт SmartCaptcha (`yandex.ru/showcaptchafast`) даже через мобильный egress — скрейпить через SearXNG невозможно. yandex-движок SearXNG отключён (тормозил агрегацию).

**Решение:** официальный Яндекс через API.
- **XMLRiver** — рекомендуемый: ~₽12–25 / 1000 запросов (Yandex+Google, регионы, топ10–100). RU-оплата. https://xmlriver.com
- XMLStock XML-proxy — ~₽18/1000. Официальный Yandex Search API — ₽360–480/1000 (×100, не нужен).

**Реализация (когда дадут ключ):** добавить Yandex-источник в discover (отдельный путь в `SearxClient`/`BrandSourceFinder`): запрос к XMLRiver API → парс XML-выдачи → URL-кандидаты в `brand_source_url` (как сейчас из SearXNG). Объём discover мал → стоимость копеечная.
**Статус:** ждёт решения/ключа владельца.

## Ветка B: Wildberries-обогащение corpus (СТРОИТЬ — proper build)

**Зачем:** куча мелких РФ-брендов = тонкий JS-сайт (trafilatura не вытаскивает прозу) + 0 веб-упоминаний → grounding-gate отклоняет (deferred). Но они есть на WB с реальными фактами (название/состав/категория/характеристики). Пилот — **moncecy (id 6571)**: сайт дал 1 документ из 22 страниц → deferred; WB поиск вернул **12 товаров** (брюки палаццо, платья мини, спорткостюмы оверсайз, свитшоты, шорты — женская одежда).

**Что выяснено (важно для реализации):**
- WB **троттлит** прямой IP: повторные запросы → `HTTP 429 Too Many Requests`.
- Через **мобильный прокси** (наш `socks5://172.17.0.1:1080`, туннель на Windows-удалёнку) WB **отвечает** — но тоже с лимитами при частых запросах.
- API многошаговый и эндпоинты плавающие:
  - `search.wb.ru/exactmatch/ru/common/v5/search?query=<brand>&dest=-1257786&...` → при точном бренде возвращает `metadata.context:["brand"]` + `catalog_value: preset=<N>` (НЕ products inline), либо products при не-бренд-запросе.
  - продукты бренда — отдельный catalog-вызов (preset/brand endpoint, точный URL надо до-реверсить — `catalog.wb.ru/catalog/presets/...` у меня вернул пусто, вероятно нужен `brands/v2/catalog?brand=<brandId>`).
  - детальная карточка (описание/состав/характеристики) — `basket-XX.wbbasket.ru/volV/partP/<nm>/info/ru/card.json`, где basket-host(XX) выводится из nm по диапазонам vol (маппинг растёт со временем — хрупко).

**ТЗ на реализацию `app:brand:wb-enrich`:**
1. Все WB-запросы — **через мобильный SOCKS-прокси** (.43), с **пейсингом ≥1с** и **retry/backoff на 429** (3 попытки, экспон.). Не частить.
2. По бренду: search → получить brandId/preset → catalog → список nm (фильтр `brand == <title>`, регистронезависимо, чтобы отсечь чужие товары в выдаче).
3. (опц. v2) card.json по nm → описание/состав/характеристики (с резолвом basket-host).
4. Собрать RU-текст: «Бренд <title> на Wildberries. Ассортимент (N): <названия>. Категории: <subj>. Состав/материалы: <...>». 
5. Сохранить как `brand_source_document(brand_id, source_type='marketplace', url='wb:<brand>', text=...)`.
6. Триггернуть re-embed + re-generate (`--grounded-only`) — снимет deferred.
**MVP-достаточно:** даже только названия+категории из search дают факты для grounded-описания (без card.json).

**Риски:** WB анти-бот (нужен прокси + backoff + возможно ротация IP); эндпоинты/basket-маппинг меняются (нужна устойчивость к смене + логирование). Не делать «в лоб» частыми запросами — забанит IP.

**Instagram — НЕ делаем:** нет открытого API, жёсткий анти-бот, нужен логин/куки, риск ToS; bio/посты дают мало пользы. Максимум — разовый ручной fetch конкретного поста.

**Статус:** концепт доказан (WB-данные есть и достижимы через прокси). Полноценную реализацию вынести в отдельную сфокусированную задачу (не в марафон-сессию) — нужна аккуратная RE текущих WB-эндпоинтов + backoff.
