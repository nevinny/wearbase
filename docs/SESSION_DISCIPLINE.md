# Дисциплина сессии

**Читать в начале КАЖДОЙ сессии, до первой правки кода.** Документ описывает две
вещи: как не уйти в бесконечный рефакторинг и куда девать всё, что всплыло по пути.

---

## 1. Правило одной задачи

> Мы платим за закрытие этой задачи, а не за исправление архитектуры проекта.

Монолит большой и местами грязный. Если сканировать всё подряд, проблемы найдутся
в половине файлов, и сессия утонет. Поэтому:

- **Область работы объявляется в начале и не расширяется по ходу.** Три-пять файлов.
  Всё, что за их пределами, — не предмет этой сессии.
- **Запрещено внутри задачи:** рефакторинг «заодно», переименование переменных,
  смена сигнатур, приведение соседнего кода к стилю, починка соседнего бага.
- **Критерий завершения задаётся заранее** и формулируется проверяемо: проходит
  такой-то тест, ручка отдаёт такой-то ответ, страница рендерится. Без явного
  критерия оценка «достаточно ли хорошо» становится бесконечной.
- **Костыль разрешён**, если задача локальная и правильное решение тянет за собой
  чужие модули. Помечается `// FIXME: костыль <дата/тикет> — убрать после <что>`
  и заводится задачей (§2). Осознанный костыль с запиской лучше, чем недельный
  рефакторинг ради однострочного бага.

## 2. Куда девать всё, что всплыло по пути

Побочные находки — ценность, но не повод переключаться. Каждая находка **заводится
отдельной задачей** и забывается до своей очереди:

```bash
python3 tools/tasks/task.py new "<что не так, одной строкой>" --source "<откуда>"
```

Это и есть «бэклог внезапностей». Отдельного файла для него нет намеренно: находка,
записанная задачей с номером, не теряется и не мешает текущей работе. Заводить —
сразу, одной строкой, без анализа глубины. Анализ — когда до задачи дойдёт очередь.

**Не делать:** не описывать находку в ответе пользователю вместо задачи (потеряется
при закрытии вкладки), не начинать её чинить, не расширять текущий MR.

## 3. Трекер задач: одна задача — один файл

Живёт в `docs/tasks/`. Пришёл на смену `docs/tasktracker.md`, который при
параллельных сессиях затирался: один файл на 44 КБ, 71 коммит за 30 суток, записи
перезаписывали друг друга.

```
docs/tasks/
├── INDEX.md          ← ГЕНЕРИРУЕТСЯ, руками не править
├── 0001-slug.md      ← активные
├── 0002-slug.md
└── done/
    └── 0003-slug.md  ← завершённые, имя файла не меняется
```

**Почему так, а не одним файлом:** общей точки записи нет вовсе. Каждая сессия
пишет только в свой файл, поэтому конфликтов и затирания не бывает по устройству,
а не по договорённости.

### Команды

```bash
python3 tools/tasks/task.py new "<заголовок>" [--owner NAME] [--source TEXT] [--status STATUS]
python3 tools/tasks/task.py done <NNNN>      # перенести в done/
python3 tools/tasks/task.py reopen <NNNN>    # вернуть в активные
python3 tools/tasks/task.py index            # пересобрать INDEX.md
python3 tools/tasks/task.py list [--status S]
```

### Правила

- **Номер выделяется атомарно.** Скрипт создаёт файл с флагом «только если не
  существует»; если соседняя сессия успела занять номер, берётся следующий. Руками
  номера не назначать — вернётся та же гонка, ради ухода от которой всё затевалось.
- **`INDEX.md` генерируется.** Правки в нём затрутся при следующем `index`. Нужно
  поменять статус — правится шапка самой задачи, потом `task.py index`.
- **Статус живёт в шапке задачи** и больше нигде. Значения: `новая`, `в работе`,
  `ждёт решения`, `сделана`, `отменена`.
- **Имя файла при переносе в `done/` не меняется** — номер остаётся грепаемым,
  а ссылки вида «задача 0042» продолжают работать.
- **Одна задача — один владелец в моменте.** Если две сессии трогают одну задачу,
  правит та, что указана в `owner`; вторая заводит свою и ссылается номером.
- **Задача пишется для того, кто прочтёт её через месяц без контекста:** что не так,
  чем грозит, где смотреть (файлы со строками, MR, таблицы).

### Старый трекер

`docs/tasktracker.md` **заморожен**: он остаётся как архив, новые записи туда не
добавляются. Задачи из него переносятся в `docs/tasks/` по мере того, как до них
доходят руки, — разово мигрировать 44 КБ смысла нет.

## 4. Что должно остаться после сессии

Перед закрытием вкладки в диалоге не должно быть незакрытых концов. Проверить:

- **Ветки запушены** либо их существование явно записано задачей. Незапушенная
  ветка — самая частая потеря: она не видна ни в экспорте, ни в трекере.
- **Незакоммиченное** (`git status`, `git stash list`) — либо забрано, либо описано.
- **Побочные находки** заведены задачами (§2), а не оставлены в тексте ответа.
- **Написанные, но не отправленные тексты** (ответы в чаты, комментарии в MR) —
  сказано явно, где лежат и что не отправлены.
- **Изменения на проде**, если были, зафиксированы отдельной строкой: что именно,
  когда, чем проверено.

## 5. Когда контекст уже отравлен

Если сессия ушла вглубь и в контексте висит десяток вскрытых проблем — чинить это
внутри диалога бесполезно. Забрать текущий дифф, открыть новую сессию, дать в неё
только дифф и критерий завершения. Всё вскрытое по пути к этому моменту уже должно
лежать задачами в `docs/tasks/` — за этим и нужен §2.
