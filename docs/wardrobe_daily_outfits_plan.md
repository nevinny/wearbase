# План 1. Ежедневные AI-образы из загруженных вещей

Дата: 2026-09-13. Статус: план реализации, код не изменён.
База проверки: `origin/main` (`b9b65f3`), а не устаревшая локальная
`feature/wardrobe-manual-outfit-builder`. Наличие кода не подтверждает деплой.
Связанный документ: [подготовка вещей](wardrobe_item_preparation_plan.md).

## Цель и пользовательский сценарий

Утром человек открывает «На сегодня» и видит до трёх пригодных образов из своего
гардероба: основной и альтернативы. Выбирает образ, при необходимости заменяет вещь,
после носки отмечает факт и комфорт. Следующий подбор учитывает подтверждённую историю.
Для ребёнка используется его гардероб и профиль, действия родителя фиксируются отдельно.

Первая версия: ежедневный экран с подготовкой по запросу. Следующий этап — добровольная
автоматическая подготовка к выбранному времени с учётом часового пояса.
Результат — коллаж из реальных фотографий вещей, названия и короткое объяснение.
Виртуальная примерка не является условием запуска ежедневного подбора.

## Что уже есть

- `WardrobeOutfitService`: до трёх предложений, проверка ID по переданному каталогу,
  local-first и remote-путь с проверкой согласия владельца профиля.
- `WardrobeStylistContextBuilder`: активные, носимые, чистые вещи; событие,
  заданная пользователем погода и температура; приоритет вещей без недавних носок.
- `WardrobeOutfitLearningService`, история образов и `WardrobeWearEvent`:
  существующая основа персональных предпочтений и подтверждённых носок.
- Ограничение каталога в prompt: 80 вещей. Это требует отбора кандидатов,
  иначе большой гардероб представлен лишь частично.

## Этапы

### 1. Данные и правила пригодности

Принять минимальный контракт из плана 2: владелец, ID, категория/роль, цвет,
сезон либо явное «неизвестно», текущая доступность и фото для показа.
Переиспользовать существующие фильтры чистоты, статуса и носимости.
Неизвестный материал не блокирует подбор; отсутствие обязательной роли в гардеробе
даёт понятное сообщение о недостающей вещи, без выдуманных предметов.

Уточнить повод и погодный контекст. В MVP — существующий ручной ввод.
Автоматическую погоду добавить отдельно: выбранный город, дата и свежесть прогноза;
при ошибке источника предложить ручной ввод. Не утверждать пригодность к погоде,
если она неизвестна.

Готово: вещи другого профиля, удалённые, грязные, малые и недоступные не попадают в кандидаты.

### 2. Качественный подбор и проверка результата

Отбирать кандидатов по функциональным ролям и контексту до ограничения в 80 вещей.
Поддержать схемы «верх + низ + обувь» и «цельная вещь + обувь»; слои и аксессуары
добавлять по ситуации. Схемы расширять для спорта и других подтверждённых сценариев.
Историю носок использовать как мягкий приоритет, чтобы маленький гардероб не остался без образов.

Передать LLM структурированный каталог и предпочтения. После ответа на сервере
проверить ID, доступ, актуальную доступность, комплектность, дубли вещей и дубли образов.
Отклонять неподходящий образ целиком: простое удаление неверного ID может оставить
неполный комплект. Разрешить один ограниченный повтор, затем объяснить отсутствие результата.

Готово: каждый показанный образ проходит серверные правила; никаких вещей вне каталога.

### 3. Экран «На сегодня» и замена вещи

Сохранить дату в часовом поясе владельца, исходный контекст и версию входных данных.
Показывать сохранённый дневной результат при повторном открытии.
Добавить «Надену», «Заменить вещь», «Другой вариант» и переход к карточкам вещей.
«Надену» — план; факт носки подтверждается отдельным действием через существующий журнал.
При замене сохранять остальные вещи и снова валидировать комплект.

Изменение погоды, статуса вещи или гардероба помечает подбор устаревшим.
Перед показом и подтверждением повторно проверять доступность и права.
Исторический snapshot сохранять, но он не даёт права предлагать уже удалённую вещь.

Готово: обновление страницы не вызывает новый LLM-запрос; план не создаёт ложную носку.

### 4. Автоматическая ежедневная подготовка

Настройки: включение, время и часовой пояс на профиль. Расширить существующий механизм
фоновых команд: одна задача на профиль и локальную дату, атомарный захват,
ограниченные повторы и восстановление после сбоя. Учесть смену часового пояса и переход даты.
Повторный запуск не создаёт дубли и не затирает уже выбранный образ.

Сначала готовить результат внутри приложения. Уведомления подключить отдельным шагом
по выбранному пользователем каналу; отправлять только после успешной подготовки.

Готово: конкурентные запуски создают один дневной набор; выключение настройки прекращает новые задачи.

### 5. Пилот и улучшение предпочтений

Пилот: один взрослый профиль, затем доступный детский; 7–14 дней реального использования.
Учитывать подтверждённые носки, комфорт и причины замены через существующую память.
Не трактовать лайк как носку, а чужое действие — как собственное мнение ребёнка.

Метрики: выбранные и реально надетые образы / показанные, доля замен, причины отказа,
время ожидания p50/p95, ошибки, стоимость запроса и доля повторно использованных результатов.
Целевые продуктовые значения установить после первой недели базовых измерений.

## Инфраструктура и проверки

Осмотр рига 2026-09-13: Ollama 0.33.2, загружена `gemma4:26b`, контекст 8192;
доступность API подтверждена, качество и скорость генерации ещё не измерялись.
Перед интеграцией выполнить короткий тест JSON-ответа и замер на реальных каталогах.
Не выбирать модель только по её имени. Сохранить конфигурируемый выбор провайдера.

Тяжёлые задачи рига выполнять последовательно, дневным запросам дать приоритет
перед массовой обработкой фото. Межпроектную очередь/блокировку сначала проверить:
локальный flock команды импорта не защищает от другого AI-потребителя.
При недоступности рига показать актуальный сохранённый результат либо состояние ожидания;
remote использовать только в рамках существующего согласия и бюджета.
Qdrant не требуется для первого запуска: SQL-фильтров и существующей памяти достаточно.

Проверки: права семейных профилей, неполный гардероб, более 80 вещей, грязная/удалённая
вещь после генерации, неверный JSON/ID, одинаковые альтернативы, смена даты,
конкурентные задачи, сбой LLM, запрет remote, отсутствие двойной записи носки.
