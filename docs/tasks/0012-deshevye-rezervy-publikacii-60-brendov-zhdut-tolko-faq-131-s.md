## Суть

Два дешёвых резерва для остановившейся очереди публикации (см. задачу 0011): 60 брендов в статусе `done`, у которых единственный блокер — `faq_status IS NULL`; 131 бренд на проде с `status='new'`, `publish_pending=0`, гейты проходят, `published_at` NULL, у 128 есть description и meta.

## Почему это важно

Прогон `app:brand:faq` даёт 60 новых карточек = 0.75 дня дрипа при темпе 80/день. Флип флага `publish_pending` у 131 бренда дал бы ещё 1.6 дня дрипа. Суммарно оба резерва — около 2.5 дней, это не решение проблемы пустой очереди (см. задачу 0011), а отсрочка.

## Где смотреть

- `BrandIngestService` — зовёт `Brand::queue()` (ставит `publish_pending=1`) только при СОЗДАНИИ бренда (строка ~53), апдейт существующей записи флаг не трогает
- `BrandPublishSyncCommand:154` (Mac) — единственный `setPublishPending(false)` в коде

## Что сделать

- [ ] прогнать `app:brand:faq` по 60 брендам с `faq_status IS NULL`
- [ ] ДО флипа 131 бренда с `publish_pending=0` разобраться, как они оказались в этом состоянии (иначе повторится)
- [ ] проверить, не сняты ли эти 131 бренд с публикации намеренно

## Заметки

Наполнение очереди по существу требует перезапуска конвейера, а не разбора резервов: discover последний раз работал 20.08, RAG-кроны на Mac отключены с 23.06.
