# Жизненный цикл бренда: ниша-гейт + HTTP-семантика (410/tombstone)

> Гигиена каталога: автоматически отсекать бренды **не из ниши** (мода + красота) до того,
> как они опубликуются или под них сгенерится контент, и отдавать корректные HTTP-сигналы
> для удалённых и закрывшихся брендов.
> Справочник команд (cron, как часто/где) — [commands.md](commands.md); устройство RAG-конвейера,
> в который встроен гейт, — [rag_pipeline.md](rag_pipeline.md).

## 1. Зачем это

Повод — `wearbase.ru/ru/brands/apadent` отдавал 404. Разбор: **apadent — японская зубная
паста** (Sangi, нано-гидроксиапатит), случайно затянутая импортом лидов в каталог одежды;
RAG даже сгенерил ей описание про эмаль. Аудит 2026-06-24 показал, что это не частный случай:

- ≥759 из 6724 `new`-лидов и ≥29 `active` (живых, в индексе, в sitemap) брендов имеют явные
  не-fashion маркеры в keywords (нижняя граница по грубой эвристике);
- примеры: `aprel` (аптека «Апрель», 755k показов/мес), `dreame`/`dyson`/`tefal` (пылесосы),
  `galaxy`/`samsung` (смартфоны), `askona`/`mir-matrasov` (матрасы), `oral-b`/`elmex`/`apagard`
  (зубная паста).

Спрос у них реальный, но **чужой**: привести «купить зубную пасту» в каталог одежды = отказы +
размытие тематичности домена. Корень — импорт лидов ([import-leads](commands.md), NJAL/РБК/
local-brands) + сбор Wordstat затянули нерелевантные бренды, а в конвейере
`discover→…→generate→publish` **не было ниша-гейта**. Плюс любой неопубликованный/удалённый
бренд отдавал общий 404 — слабый сигнал на деиндексацию.

## 2. Что такое «ниша»

WEARBASE — каталог **МОДЫ + КРАСОТЫ**:

| `in` (в нише) | `off` (чужая ниша) |
|---|---|
| одежда, обувь, сумки, аксессуары, ювелирка/бижутерия | аптечные сети, лекарства/БАД, гигиена полости рта (зубные пасты/щётки) |
| косметика, уход за кожей/волосами, парфюмерия | бытовая техника и электроника, мебель и матрасы |
| | авто и запчасти, продукты и напитки, стройматериалы, товары для дома/сада, зоотовары |

Решение «**косметика = in**» принято осознанно (estel/bioderma/aravia/anua проходят) — это
смежная и желанная аудитория. Зубная паста/гигиена — `off` (это не косметика, а уход/медицина).

## 3. Классификатор `app:brand:niche-check`

`src/Command/NicheCheckCommand.php`. Выносит вердикт `in`/`off` и пишет в `brand.niche_status`.
**Недеструктивен** (кроме явного `--set`).

**Два пути вердикта:**
1. **Фаст-путь по маркерам** (без LLM) — однозначно не-fashion и не-косметика слова в keywords
   или title (`пылесос`, `смартфон`, `матрас`, `аптека`, `автомобил`, `корм для`…). Reason =
   `marker:<слово>`. ⚠️ В списке **нет** «крем/паста/шампунь» — они beauty-неоднозначны, их
   решает LLM.
2. **Локальная LLM** (ollama, как `generate-content`) — для остального. Контекст: title,
   tagline/anons, ~400 символов описания, топ-5 keywords. Просим строгий JSON
   `{"verdict":"in|off","reason":"…"}`. Невалидный JSON → бренд **не помечается** (повторим позже).

**Опции:**

| Опция | Назначение |
|---|---|
| `limit` (arg, 100) | сколько брендов за прогон |
| `--status=new\|active\|all` | какие статусы брать (по умолчанию all) |
| `--id=N` | один бренд |
| `--dry-run` | показать вердикты, не записывать |
| `--force` | перепроверить уже классифицированные |
| `--set=in\|off\|closed\|reopen\|delete` | **ручное действие** (только с `--id`): override вердикта / `close()` / `reopen()` / `softDelete()` |

**Выборка:** `niche_checked_at IS NULL` (или `--force`); порядок — `active` первыми, внутри — по
убыванию суммарного Wordstat-спроса (высокотрафиковый шум ловим раньше). В конце прогона —
сводка + **отдельный список active-off-niche** (живые бренды для ручного решения).

## 4. Гейт конвейера и публикации

`niche_status='off'` исключает бренд из обработки. `NULL` (не проверен) и `in` — проходят
(иначе гейт застопорил бы дрип до прогона классификатора).

| Точка | Файл | Как |
|---|---|---|
| **Весь RAG-конвейер** (scrape/embed/generate/extract/faq/push/keywords/logo/…) | `PipelineQueueRepository::finishStageQuery` | единая точка: `b.nicheStatus IS NULL OR b.nicheStatus != 'off'` |
| **Дрип-публикация** | `PublishTickCommand` (raw SQL выбора) | `AND (niche_status IS NULL OR niche_status <> 'off')` |

Так off-niche `new`-бренд никогда не публикуется и не тратит scrape/LLM (как было с apadent).

> **Active off-niche НЕ снимается автоматически** — только помечается. Возможны false-positive
> LLM; снятие = ручной `--set=delete` после ревью.

## 5. HTTP-семантика страницы бренда

`BrandsController::show()`. Привилегированным (участник бренда / `AdminAccess::isAdmin()`) —
превью любого бренда.

| Состояние | Ответ | Что видит гость |
|---|---|---|
| `status=deleted` | **410 Gone** + noindex | `tailwind/brand/gone.html.twig` — «страница удалена», ссылки на каталог |
| `status=active` + `closed_at` задан | **200** | tombstone-плашка «Бренд прекратил работу» + блок похожих **действующих** брендов; страница остаётся в индексе |
| `status=active`, не закрыт | **200** | обычная страница |
| `status=new\|disabled\|system` | **404** | как в каталоге/sitemap (это НЕ «удалено навсегда») |

Логика: `deleted` = удалён навсегда → 410 (чёткий сигнал на деиндексацию, быстрее 404).
`niche_status=off` **сам по себе HTTP не меняет** — деиндексация наступает, когда человек делает
`--set=delete` (→ `deleted` → 410).

**Tombstone** — для реально закрывшихся fashion-брендов с хвостом спроса («бренд X отзывы/что
случилось»): 404 такой спрос выбросил бы в мусор, а 200-надгробие удерживает SEO-трафик и
конвертит в живые бренды. Авто-триггера нет (в данных нет сигнала «закрылся») — пометка вручную
`--set=closed`.

## 6. Модель данных

Миграция `Version20260624_brand_lifecycle`. Поля на `brand`:

| Поле | Тип | Смысл |
|---|---|---|
| `niche_status` | `VARCHAR(12)` NULL | `NULL`=не проверен, `'in'`, `'off'` (индекс `idx_brand_niche`) |
| `niche_reason` | `VARCHAR(255)` NULL | обоснование: `marker:пылесос` или фраза от LLM (для ревью) |
| `niche_checked_at` | `DATETIME` NULL | когда вынесён вердикт |
| `closed_at` | `DATETIME` NULL | бренд прекратил работу (tombstone); `NULL`=действующий |

Хелперы на `App\Entity\Brand` (рядом с машиной состояний статуса): `getNicheStatus()`,
`isOffNiche()`, `markNiche($verdict, $reason, $at)`, `getClosedAt()`, `isClosed()`,
`close($at=null)`, `reopen()`.

## 7. Эксплуатация

**Порядок cron:** `app:brand:niche-check` → `app:brand:publish-tick`. Гейт пропускает
непроверённые (`niche_status IS NULL`), чтобы не стопорить дрип, — значит пометка `off` должна
успеть до публикации.

```bash
# Бэкафилл всего каталога (разово; ~7k LLM-вызовов, долго; --no-debug против OOM профайлера)
php -d memory_limit=512M bin/console app:brand:niche-check 7000 --no-debug

# Сначала разгрести живые (в индексе) off-niche
php bin/console app:brand:niche-check --status=active 500 --dry-run

# Снять подтверждённый off-niche бренд (→ deleted → 410)
php bin/console app:brand:niche-check --id=1081 --set=delete

# Пометить закрывшийся fashion-бренд надгробием (страница остаётся 200)
php bin/console app:brand:niche-check --id=NNN --set=closed
```

После бэкафилла — глазами пройтись по списку active-off-niche из вывода и решить
`--set=delete`/оставить.

## 8. Подводные камни

- **Бэкафилл ~7k LLM-вызовов** на локальном сервере (IP непостоянен — см. CLAUDE.md / RAG).
  Фаст-путь по маркерам срезает часть; остальное идёт батчами/через автоскейлер.
- **False-positive LLM** — поэтому active off-niche только помечаем, не снимаем; reason храним.
- **Гейт пропускает `NULL`** намеренно — иначе непроверенные бренды застрянут в конвейере.
  Отсюда требование к порядку cron.
- **Тест-БД (SQLite)** строится схемой, а не миграциями: новые колонки в `*_test` надо добавить
  вручную (`dbal:run-sql --env=test "ALTER TABLE brand ADD COLUMN …"`), иначе функциональные
  тесты `NicheLifecycleControllerTest` падают на отсутствующей колонке.
