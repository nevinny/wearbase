# Выбор хостинга: уход с reg.ru shared на VPS

> Разбор от 2026-08-20. Задача: снять лимит «7 сайтов» reg.ru, получить место и БД без ограничений,
> оставить рабочим TG-egress и прокси домашней LLM. Проекты: wearbase.ru, minerdash.ru, drugs (в разработке)
> + быстрые лендинги под гипотезы (домен → лендинг за 1–2 вечера).

### Что из этого следует

**Вся задача стоит от −408 до +1 872 ₽/год — это шум.** Оптимизировать нечего, поэтому
**решение принимается по лимитам и рискам, а не по цене.** Однозначные выводы всё же есть:

- **D — единственный дорогой сценарий**: +4 512 ₽/год, и это ещё до 152-ФЗ. Отпадает по деньгам
  раньше, чем по юридике.
- **E — реальный ценовой пол (641₽)** и единственный вариант, не решающий задачу: фиксирует
  потолок 7/7 сайтов на 3 года. Формулировка честная: **возможность запускать лендинги без
  ограничений стоит +188 ₽/мес над этим полом** (829 vs 641). Это и есть цена вопроса.
- **B дешевле того, что платится сейчас** (829 против 863). Апгрейд до root, 50 ГБ NVMe вместо
  13 ГБ и снятых лимитов достаётся бесплатно, даже с экономией.

Мелким шрифтом:

- Бэкапы на VPS — наши: `mysqldump` + restic в Selectel S3, ~20 ГБ × 1.5₽ ≈ **+30 ₽/мес**.
  С ними B = 859₽ — по-прежнему уровень текущего.
- ⚠️ **Промо 1.99 € у Aeza при продлении почти наверняка станет обычной ценой** — заложить рост
  этой строки. Ещё один довод держать egress на rustelekom-shared (179₽ — обычный тариф), как в B.
- Курс взят 95 ₽/€; при 105 aeza = 209₽ — на выводы не влияет.
- ⚠️ **Не продлевать reg.ru на 36 месяцев** ради скидки 45%: 271.69₽/мес — это фиксация на 3 года
  тарифа с потолком, в который мы уже упёрлись. Максимум — 1 месяц на время переезда.

### Чем платим на самом деле

Деньги — не та валюта, в которой оплачивается этот переезд. Сравнение ресурсов за похожие деньги:

|---|---|---|
| Диск | 13 ГБ | **50 ГБ NVMe** (×3.8) |
| Файлы (inode) | 150 000, занято 116 389 | **без лимита** |
| Сайтов | **7, занято 7** | **без лимита** |

| Root / SSH | нет | **есть** |

Плата — **эксплуатация, которую раньше делал провайдер**: первичная настройка (панель, PHP, MySQL,
vhost'ы, SSL, секреты деплоя, миграция данных) ≈ 4–6 часов, дальше ~1–2 часа в месяц на обновления
безопасности и проверку бэкапов. И аптайм становится нашей ответственностью: некому починить nginx
в 3 часа ночи. Это осознанный обмен часов на снятые потолки, а не бесплатный апгрейд.

## Ключевой вывод про лимиты

Любой shared-хостинг = лимит сайтов + лимит inode. Symfony-проект это ~30–60k файлов на инсталляцию
(`vendor/` + `var/cache/`), поэтому «купил домен → поднял лендинг» на shared физически не масштабируется:
третий-четвёртый Symfony-проект добьёт inode-квоту даже там, где сайты «не ограничены».
**Правильный ответ — свой VPS: ни сайтов, ни inode, ни БД не считают.**

## Санкционный риск Aeza — не размещать там tier-1

1 июля 2025 OFAC внёс **Aeza Group LLC** в SDN-лист как bulletproof-хостинг (хостил Meduza/Lumma
infostealer). Под санкции попали 4 руководителя, UK-прокладка и TRON-кошелёк платёжной инфраструктуры.
Практические последствия для нас:

- риск отключения апстримами/платёжками в любой момент → проект уезжает вместе с провайдером;
- IP-диапазоны такого ASN попадают в blocklist'ы (Spamhaus и пр.) → **убитая доставляемость email**
  и повышенная вероятность капч/блоков у Cloudflare, платёжек, API;
- репутационный риск для домена в глазах поисковиков и партнёров.

**Решение:** aeza-бокс оставляем как есть — под VPN для себя (1.99€ за 4 ГБ RAM это подарок),
но **ни wearbase, ни minerdash, ни почта туда не переезжают**.

Четыре причины не переносить туда tier-1:

1. **152-ФЗ, ст. 18 ч. 5 — блокер.** Первичный сбор и хранение ПД граждан РФ обязаны идти на серверах
   **в России**. У wearbase есть аккаунты, заказы, адреса доставки → мы оператор ПД. Дублировать за
   границу можно, первично собирать — нет. Штраф юрлицу **1–6 млн ₽** (повторно 6–18 млн).
   Хельсинки/Амстердам для wearbase.ru — это осознанное нарушение с несоразмерным риском.
2. **Яндекс.** Весь наш рост — SEO-канал (см. proof_pack.md). Латентность Амстердам→РФ ~40–50 мс поверх
   каждого запроса + региональный фактор. Ухудшать скорость основного канала роста за деньги — плохая сделка.
3. **Цена/спек.** 679₽ за 2 ГБ SSD против 650₽ за 4 ГБ NVMe в Selectel. Mars (2 ГБ) под MySQL 8.4 +
   PHP-FPM + наши батчи (`-d memory_limit=512M`) будет свопить. Реальный минимум — Earth за 1049₽,
   то есть ×1.6 к Selectel за худший диск. Переплата идёт за локацию, а не за железо.
4. **Репутацию ASN подтвердить не удалось** — в отличие от Aeza публичных санкционных/abuse-данных по
   rustelekom не нашлось. Не обвиняем, но и не считаем проверенным: перед постановкой чего-либо
   значимого прогнать IP через check.spamhaus.org и mxtoolbox.

**Где rustelekom реально полезен:** как *исходящий* egress-узел (TG, API, блокирующие RU-IP). Для этой
роли уже оплаченного shared за 179₽ достаточно, а Mars за 679₽ — четырёхкратная переплата за прокси.

## Рекомендуемая схема

```
┌─ Selectel VDS 2-4-50 (650₽) — Москва ─────────────┐
│  wearbase.ru      (Symfony 7.3, MySQL 8.4 LTS)    │
│  minerdash.ru                                     │
│  drugs.* (dev)                                    │
│  N лендингов-гипотез  ← новый vhost за 5 минут    │
│  cron-диспетчер app:cron:run-scheduled  ← с Mac   │
└───────────────────────────────────────────────────┘
┌─ egress наружу ───────┐   ┌─ Cloudflare Tunnel (0₽) ─┐
│  TG / API, блокирующие │   │  домашняя LLM → наружу   │
│  RU-IP. Варианты:      │   │  без открытых портов и   │
│   • aeza ~190₽ (есть)  │   │  без static IP           │
│   • rustelekom shared  │   └──────────────────────────┘
│     179₽ (есть)        │
│  НЕ Mars за 679₽       │
└────────────────────────┘
```

**Почему Selectel 2-4-50 как база:** это строго лучше текущего reg.ru за +156₽ — root, 50 ГБ вместо 13,
нет лимита сайтов, нет лимита inode, свои БД. CPU-запас избыточен уже сейчас (3% нагрузки на shared).
Апгрейд до 4-8-80 делается в панели, когда батчи RAG/импортов реально начнут упираться в 4 ГБ.

**Панель для «лендинг за вечер»:** поставить **FASTPANEL** (бесплатная, RU) или HestiaCP на чистую
Ubuntu 24.04 **до** размещения сайтов. Создание сайта = vhost + Let's Encrypt + БД + FTP в пару кликов.
⚠️ Для Symfony нужен свой шаблон vhost (`root` → `public_html`, `try_files` → `index.php`) — иначе
панельный дефолт не поднимет фронт-контроллер. Не смешивать панельные и руками написанные конфиги nginx.

**Бэкапы — теперь наша ответственность** (на shared их делал провайдер): nightly `mysqldump` + restic/rclone
в Selectel S3 (~1.5₽/ГБ) плюс снапшоты провайдера. Без этого VPS — регресс по надёжности, а не апгрейд.

## TG-egress: сначала проверить, потом платить

В `docs/production.md` зафиксировано: TG-egress **с прода regru работает** (проверено 2026-07-11),
webhook-бот отвечает с прода; с Mac уходят только массовые рассылки.

Поэтому порядок действий: подняли Selectel → **`curl -m 10 https://api.telegram.org` с него** →
если 200, то rustelekom (179₽) закрывается совсем, прокси не нужен.
Если заблокировано — socks5 (3proxy) на уже оплаченном aeza-боксе; для исходящего прокси
санкционный ASN безвреден (наружу светится не наш сайт, а прокси).

**Домашняя LLM:** вместо прокси через хостинг — `cloudflared` tunnel с самого LLM-сервера.
Бесплатно, без открытых портов и, главное, **лечит нашу постоянную боль с плавающим IP**
(192.168.2.43 → .0.119 → .0.111): туннель переподключается сам, DNS-имя стабильно.

### Пересмотр от 2026-08-20: продление на месяц — базовый вариант, а не страховка

Реальные вводные: свободного времени сейчас нет, автор в деревне со слабым каналом, в Москве будет
через 5–7 дней (то есть 25–27.08). Остаток до 06.09 сжимается до 10–12 дней, и главное — **исчезает
окно бесплатного откката**: переключение DNS уезжает на 02–03.09, оставляя 3–4 дня на «что-то пошло не так»
по семи сайтам сразу.

**Решение: продлить reg.ru на 1 месяц (494₽) и перенести переезд на спокойный октябрь.**
Дедлайн 06.09 — искусственный, и он удаляется за 494₽. Гонка ради экономии 494₽ при риске уронить
семь сайтов без пути назад — плохая сделка. Продлевать **только на 1 месяц**: 6/12/36 месяцев
фиксируют потолок 7 сайтов, в который мы уже упёрлись.
⚠️ Решение принять **до 06.09** — после истечения тариф уходит в suspend, а не ждёт нас.

### Слабый канал переезду почти не мешает

Важное уточнение, снимающее половину опасений: **основной объём данных идёт дата-центр → дата-центр,
а не через ноутбук.** rsync напрямую между двумя удалёнными хостами не умеет, поэтому тянем **с нового
сервера**:

```bash
ssh selectel 'rsync -avz regru:/path/public_html/images/ /path/public_html/images/'
ssh selectel 'ssh regru "mysqldump -u… db | gzip" | gunzip | mysql db'
```

Через наш канал уходят только команды (килобайты). Что действительно страдает от плохого интернета —
длинные интерактивные сессии и отладка в браузере, поэтому:
⚠️ **все долгие операции запускать в `tmux` на сервере** — обрыв SSH не убьёт миграцию на середине.

### Что стоит сделать из деревни (2 минуты, нулевой трафик)

1. `dig MX wearbase.ru` и по остальным доменам — **если почта на хостинге reg.ru, 06.09 умрёт и она.**
   Это единственное, что нельзя обнаружить постфактум.
2. Узнать у поддержки reg.ru политику после истечения: сколько дней suspend до удаления данных.
   От этого зависит, есть ли у нас запас поверх 06.09 или его нет.

⚠️ **Две вещи проверить до того, как дать хостингу истечь:**

1. **Почта.** Если MX-записи или ящики висят на хостинге reg.ru — с истечением тарифа умрёт почта,
   а не только сайты. Проверить `dig MX` по каждому домену и выгрузить ящики заранее.
2. **Регистрация доменов — это отдельная услуга** и с хостингом не истекает. Домены останутся
   в reg.ru как у регистратора, паниковать не нужно; переносить их никуда не обязательно.

⚠️ **Объём работ — 7 сайтов, а не один.** Перед началом составить инвентарь: домен → корень →
БД → крон → внешние интеграции. wearbase самый сложный (Symfony + Actions + cron), остальные проще.

## Чек-лист миграции wearbase

1. Ubuntu 24.04 → FASTPANEL → PHP 8.3/8.4 (репозиторий sury/ondrej) → MySQL.
   ⚠️ **На проде сейчас MySQL 9.1 — это innovation-релиз с коротким сроком поддержки.**
   Целиться в **8.4 LTS**; перед дампом проверить, нет ли 9.x-only синтаксиса в миграциях.
2. Перенос: `mysqldump` + rsync `public_html/images/` (логотипы/фото брендов — самое тяжёлое).
   → verify: главная, страница бренда, каталог, `/admin` открываются на новом IP через hosts.
3. GitHub Actions деплой уже rsync-овый → меняем только секреты `DEPLOY_*` и путь.
   → verify: тестовый PR в main деплоится на новый сервер, smoke зелёный.
4. Cron: перенести `app:cron:run-scheduled` (ежеминутный) с Mac на VPS.
   На Mac остаются только задачи, которым нужна домашняя LLM (или увести и их через туннель).
5. DNS: TTL 300 за сутки до переключения; старый reg.ru держать живым неделю после.
   → verify: логи nginx на старом хосте пусты → отключаем.
6. Почта: свежий IP VPS для SMTP непригоден — продолжаем отправлять через релей
   (см. env-карту в docs/production.md), напрямую с сервера не слать.
