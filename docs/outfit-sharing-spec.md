## 1. Share-механика

### 1.1 Токен
- Opaque random: `bin2hex(random_bytes(32))` → 64 hex-символа = **256 бит энтропии** (требование ≥128 бит перекрыто; совпадает с доменным паттерном `BrandInvite`/`FamilyInvite`).
- Токен ищется напрямую по индексу — **никаких инкрементальных/предсказуемых ID в URL**.
- URL: `/l/{token}` — короткий префикс вне `/account`, чтобы не пересекаться с правилами firewall.

### 1.2 Таблица `wardrobe_outfit_share` (sketch)

```sql
CREATE TABLE wardrobe_outfit_share (
    id            INT AUTO_INCREMENT PRIMARY KEY,
    outfit_id     INT NOT NULL,
    token         CHAR(64) NOT NULL,               -- bin2hex(random_bytes(32)), UNIQUE
    created_by_id INT NOT NULL,                    -- actor (владелец или родитель ребёнка)
    granted_at    DATETIME_IMMUTABLE NOT NULL,
    expires_at    DATETIME_IMMUTABLE NULL,         -- TTL; NULL = без срока (опция)
    revoked_at    DATETIME_IMMUTABLE NULL,         -- отзыв владельцем
    view_count    INT NOT NULL DEFAULT 0,          -- внутренний счётчик (§6)
    last_viewed_at DATETIME_IMMUTABLE NULL,
    UNIQUE INDEX uniq_share_token (token),
    INDEX idx_share_outfit (outfit_id),
    CONSTRAINT fk_share_outfit FOREIGN KEY (outfit_id)
        REFERENCES wardrobe_outfit (id) ON DELETE CASCADE
);
```

Сущность `WardrobeOutfitShare` повторяет стиль `WardrobeConsent`: конструктор генерирует токен и `createdAt`, fluent setters, `revoke()` ставит `revoked_at`. Одна строка = одна ссылка; повторный «Поделиться» создаёт новую ссылку (позволяет отозвать старую точечно). Альтернатива «одна активная ссылка на лук» — открытый вопрос №2.

### 1.3 Consent-тоггл владельца
- В `templates/account/wardrobe/outfits.html.twig` рядом с каждым луком — кнопка «Поделиться» (POST + CSRF `_token`, как у reaction): создаёт share и показывает абсолютный URL с кнопкой копирования.
- Отзыв: тот же блок, список активных ссылок лука с кнопкой «Отозвать» (`POST .../share/{id}/revoke`). Ревок мгновенный: гостевая страница отдаёт нейтральный 410 + `no-store` (паттерн уже принят для expired/used family claim-ссылок).
- **Для детских профилей** (`profileSubject` = managed/child User): тоггл доступен только родителю-владельцу гардероба (`FamilyService` guard), и появление кнопки дополнительно гейтится отдельным флагом «разрешить публикации» — см. §4.

### 1.4 TTL
Опции выпадающего списка при создании ссылки:

| Опция | `expires_at` | Комментарий |
|---|---|---|
| 24 часа | now +1d | дефолт для «показать маме/подруге» |
| 7 дней | now +7d | дефолт общий |
| 30 дней | now +30d | длинные обсуждения покупки |
| Без срока | NULL | явный opt-in; легко отключаемый в UI |

Истёкшая/отозванная ссылка → 410 Gone, `no-store`, без утечки факта существования лука.

## 2. Гостевой лендинг

### 2.1 Маршрут и firewall
- `src/Controller/Look/LookShareController.php` (новый публичный namespace `Controller/Look/`, аналогично существующим публичным `Brands/`, `Catalog/`).
- `#[Route('/l/{token}', name: 'look_shared_show', requirements: ['token' => '[0-9a-f]{64}'])]`.
- `security.yaml`: добавить `- { path: ^/l/, roles: PUBLIC_ACCESS }` **выше** `- { path: ^/account }`.
- Rate limit: reuse паттерна `RateLimiterFactory` (как `wardrobeAiLimiter`) на токен+IP против брутфорса.

### 2.2 Рендеринг (минимальный)
Отдельный шаблон `look/shared.html.twig`, **не** наследующий layout ЛК:
- Заголовок лука (`outfit.title`), объяснение (`explanation`) — опционально;
- Сетка карточек вещей: фото обложки + категория/цвет. Фото отдаётся **новым публичным эндпоинтом** `/l/media/{shareToken}/{photoId}` с проверкой «photo принадлежит вещи из этого share, share активен» — прямое переиспользование `account_wardrobe_media_*` невозможно (тот за firewall'ом); storage-слой (`StorageInterface`) переиспользуется как есть.
- Никогда не рендерим: имя владельца, email, синтетический `family.wearbase.local`, размеры, цены покупок, историю носок, DB-id вещей, ссылки на другие луки/гардеробы (инвариант «ребёнку не показывать чужие wardrobe links и counts» распространяем на гостей).
- Заголовки: `Cache-Control: no-store` (страница персональна), `X-Robots-Tag` по решению §5.

### 2.3 CTA «Собери свой»
1. Кнопка на лендинге → `app_register` c параметром `?ref=<shareToken>&target=/l/<token>` (см. §7).
2. Если гость уже залогинен — контроллер лендинга сразу показывает CTA «Открыть свой гардероб» вместо регистрации.
3. Возврат: `LoginSuccessHandler` уже приоритетно чтит `_security.main.target_path`; форма логина/регистрации должна пробросить `target=/l/<token>` в скрытом поле → Symfony сохранит его в сессию как target path → после входа гость возвращается на лук, теперь видя полноценную страницу. Проверить, что `RegisterController` тоже поддерживает post-registration redirect на `target` (сейчас он редиректит на dashboard) — это единственная новая проводка в auth-потоке.
4. Для уже авторизованного пользователя, пришедшего по ссылке после регистрации: лендинг сверху показывает мягкий баннер «Это лук из WEARBASE — соберите свой» с ссылкой на `account_wardrobe_outfits`.

## 3. OG-превью для Telegram/MAX

### 3.1 Обязательные теги
База уже подготовлена в `templates/tailwind/base.html.twig` (блоки `og_title`, `og_description`, `og_image`, `twitter:card summary_large_image`, фикс `1200×630`). Гостевой шаблон должен заполнить:

```html
<meta property="og:title" content="Лук: {title} | WEARBASE">
<meta property="og:description" content="{краткое описание или generic-строка}">
<meta property="og:type" content="website">
<meta property="og:url" content="https://wearbase.ru/l/{token}">   <!-- канонический, без ref -->
<meta property="og:image" content="https://.../og/{token}.png">    <!-- ABSOLUTE url -->
<meta property="og:image:width" content="1200">
<meta property="og:image:height" content="630">
<meta name="twitter:card" content="summary_large_image">
```

### 3.2 Стратегия og:image
- **Рекомендация: pre-rendered card** (серверная сборка 1200×630 через GD — в проекте уже есть опыт `imagettfbbox`/pixel-budget рендера в `GallerySlideRenderer`): сетка до 4 фото вещей на фирменном фоне + заголовок лука. Причины:
  - look-cover как таковой не существует (у `WardrobeOutfit` нет изображения);
  - коллаж скрывает лишнюю приватность: можно осознанно выбрать кадры без лиц/обрезать лица (§4);
  - предсказуемые пропорции → аккуратный превью в TG/MAX/VK/WA.
- Fallback при отсутствии фото у вещей: статичный брендированный плейсхолдер (та же карточка без фото).
- Карта генерится при создании share (или lazily при первом запросе бота) и кладётся в private storage, раздаётся тем же `/l/media/...` эндпоинтом — **не** в web-root (урок миграции legacy `/images/wardrobe*`).
- Для детских луков: og:image строится только из flat-фото; если все вещи on-person — карта без фотографий (плейсхолдер), см. чек-лист §4.

### 3.3 Cache caveats
- Telegram/MAX кэшируют og-данные по URL агрессивно и не перечитывают по обычному запросу. Следствия:
  - **Ревок не удаляет превью из мессенджера** — картинка и текст останутся в чате. Это честно проговаривается в UX («отзыв скрывает страницу, но не пересланное сообщение»).
  - Изменение title/описания лука после шаринга не подтянется — приемлемо.
  - Сброс кэша TG возможен только вручную через @webpagebot (`/updatepage`) — в поддержку не выносим, просто документируем.
  - `og:url` всегда без query-параметров (`?ref=` не попадает в превью, иначе мессенджеры закэшируют разные карты на один лук).

## 4. Приватность фото несовершеннолетних

### 4.1 Угол 152-ФЗ
- Фото ребёнка — биометрические персональные данные особой категории чувствительности при идентификации лица; обработка и уж тем более **передача неограниченному кругу лиц** (а публичная ссылка = именно это) требуют согласия законного представителя (ст. 9 152-ФЗ; для детей до 14 лет — только родитель).
- Проект уже декларирует в `docs/wardrobe_ai_learning.md` (§privacy, п.1 и правило для managed/minor): «фотографии приватны по умолчанию», публикация фото — «отдельные строгие правила», пересмотр согласия после claim/совершеннолетия. Спека обязана этой линии соответствовать, не расширять её.
- Практический вывод: шэринг лука, содержащего фото ребёнка, — **opt-in дважды**: (a) владелец гардероба (родитель) включил «Разрешить делиться детскими луками», (b) конкретная ссылка создана и подписана этим же родителем. Для managed-детей consentGrantor — только parent (`FamilyService` guard, без voter'ов — по архитектурному комментарию сервиса).

### 4.2 Parental-consent UX
- Первый раз: модал «Вы собираетесь поделиться луком ребёнка. Ссылку сможет открыть любой, у кого она есть.» + чекбокс «Я законный представитель и даю согласие на передачу фото этих вещей по этой ссылке» + выбор TTL. Фиксируем факт: `consented_by`, timestamp, id share-строки (аудит-минимум; полный журнал consent уже живёт в `WardrobeConsent` — расширять его не требуется для MVP, достаточно полей на share).
- Ребёнок с самостоятельным входом (ROLE child, не managed): кнопку «Поделиться» на своём луке показываем, но создание ссылки на лук с личными фото требует подтверждения родителя (MVP-компромисс: запретить child-initiated share фото-лука целиком, разрешить share только flat-версии — открытый вопрос №5).
- Отзыв согласия на «делиться детскими луками» автоматически отзывает все активные share его луков.

### 4.3 Чек-лист утечек (гостевой рендер + og:image)
- [ ] Лица на фото: default — отдавать фото как есть для взрослых, но og-карточку собирать из flat/обрезанных кадров; on-person детские фото в og-карте запрещены.
- [ ] Имена: `firstName` ребёнка/владельца **никогда** не попадает в title/description/alt. Заголовок лука пользовательский — предупредить в модале, что title виден получателям.
- [ ] Бренды: состав лука (категория/цвет/стиль из snapshot) можно показывать; названия брендов вещей — по умолчанию скрыть (это ещё и анти-скрейпинг каталога).
- [ ] Синтетические данные managed-профиля: email-домен, family id, claim-токены — исключены на уровне DTO.
- [ ] ID-перечисление: guest media-эндпоинт требует валидный shareToken, а не голый photoId.
- [ ] Referer/логи: URL содержит секретный токен → `no-referrer` meta на гостевой странице, чтобы токен не утекал на сторонние сайты по кликам по внешним ссылкам.
- [ ] Экспорт/скриншоты: технически не предотвращаются — честная формулировка в модале.

### 4.4 Дефолтный набор гостевых данных (рекомендация)
Видно: title лука, explanation, фото вещей (обложки), категория/цвет каждой вещи. Скрыто: имя и любой профиль владельца/ребёнка, бренды, цены, размеры, реакции, история носок, прочие луки, счётчики гардероба.

## 5. SEO: index vs noindex

**Решение: `noindex, follow` + self-canonical.**

Обоснование по матрице AGENTS.md:
- Страницы ЛК (`/account/*`) уже зафиксированы как `noindex` — гостевая страница лука это та же приватная персональная сущность, временно открытая ссылкой; добавлять в индекс её нельзя ни с точки зрения privacy (152-ФЗ, детские фото в выдаче — репутационный риск), ни с точки зрения thin content: контент = 3–6 фото + одно предложение, дублируется миллионами таких страниц.
- Токен в URL и так гарантированно вытесняет страницу из индекса со временем (боты не линкуются на секреты), но явный `noindex` нужен, чтобы ссылка, случайно попавшая на индексируемый форум, не породила индексацию.
- `X-Robots-Tag: noindex, follow` в ответе контроллера (+ `<meta name="robots">`) — надёжнее meta-only, т.к. работает и для случаев, когда страницу тянут через прокси-предпросмотр.
- Canonical: `self` (абсолютный `/l/{token}` без `?ref=` и прочих параметров) — соответствует правилу «canonical = sitemap = served URL». В sitemap **не добавляем** (❌).
- `robots.txt`: отдельно Disallow не нужен (noindex должен быть виден краулеру — Disallow как раз мешает увидеть noindex); utm/ref-параметры уже режутся правилом `Disallow: /*?utm_*`.

## 6. Кликовый трекинг без UTM

- Внутренний счётчик прямо на `wardrobe_outfit_share`: `view_count += 1` и `last_viewed_at` при каждом GET лендинга, где UA **не** матчится бот-regex — готовый паттерн уже есть в `SocialIngestClicksCommand::BOT_UA_RE` (`bot|spider|crawl|preview|vkshare|whatsapp|curl|…`), включая отсечение TelegramBot-превью. Инкремент — после отдачи ответа (`kernel.terminate` или быстрый UPDATE без транзакционных замков; contention низкий).
- Разрезка источников не нужна на MVP (одна ссылка = один канал). Если понадобится различать «TG vs WA» — создать вторую share-строку того же лука, каждый канал получает свой токен; это же даёт честную атрибуцию без UTM и без загрязнения canonical.
- Никаких `utm_*`: robots их блокирует, canonical бы рассыпался, а мессенджеры ломают параметры. `ref=`-параметр (§7) не пишется в canonical и не индексируется.
- Дашборд владельцу: на карточке лука в ЛК — «ссылок N, просмотров M, последний — date». Этого достаточно; сессионная аналитика поведения гостя сознательно не собирается — минимизация данных.

## 7. Referral attribution hook (набросок)

Лендинг принимает необязательный `?ref={shareToken}` и держит связку в сессии гостя (`$session->set('look_share_ref', $ref)`), а CTA «Собери свой» аппендит её к `/register?ref=…&target=…`; `RegisterController` после успешной регистрации (и `LoginSuccessHandler` после логина) читает этот параметр, резолвит share → получает `created_by_id` и пишет одно событие атрибуции (например, строку в будущую `referral_event`: `inviter_id, invitee_id, source='look_share', share_id, created_at`) — этого достаточно, чтобы позже экономика наград (вне scope) посчитала «привёл друга», причём механика остаётся UTM-free, канонический URL чистым, а сам hook изолирован в одном месте handoff'а лендинг→регистрация, не трогая ядро auth.

## Открытые вопросы (для product owner)

1. **TTL-дефолт**: 7 дней (рекомендация) или 24 часа? И разрешаем ли «без срока» в MVP или прячем за feature flag?
2. **Модель ссылок**: много активных ссылок на один лук (канал-на-ссылку, рекомендация) или строго одна активная с ротацией?
3. **Child-initiated share**: разрешать ли подростку с собственным входом шарить свои луки самому (с parent-confirm) или MVP только «родитель делится»?
4. **Бренды вещей на гостевой странице**: показывать названия брендов (маркетинговый плюс, но утечка состава гардероба) или скрывать (рекомендация)?
5. **«Без срока» + ревок**: устраивает ли формулировка UX «отзыв скрывает страницу, но не удалит превью из переписки» как достаточное информирование, или нужен дополнительный экран предупреждения?
6. **Атрибуция**: нужна ли запись referral-события сразу (таблица `referral_event`) или MVP ограничивается `created_by` на share, а экономика наград считается позже?
7. **Имя лука в превью**: считаем пользовательский `title` безопасным для показа получателям (рекомендация: да, с предупреждением в модале), или маскировать дефолтными «Образ дня»?

### Parent-confirm механика (решение №3)
- Колонка `status` на `wardrobe_outfit_share`: `active | pending_parent | revoked`.
- Подросток жмёт «Поделиться» → строка создаётся со статусом `pending_parent`, токен не показывается до аппрува.
- Родитель (guard через `FamilyService`) видит карточку ожидания на странице луков: «Подтвердить» → `active`, `granted_at = now`, TTL стартует; «Отклонить» → `revoked_at = now`.
- Гостевой эндпоинт отдаёт только `active`; `pending_parent` / `revoked` / истёкший → нейтральный 410 + `no-store`.
- Отзыв родительского флага «делиться детскими луками» → массовый revoke всех `active`-ссылок его луков.

### referral_event (решение №6, сразу)

```sql
CREATE TABLE referral_event (
    id INT AUTO_INCREMENT PRIMARY KEY,
    inviter_id INT NOT NULL,
    invitee_id INT NOT NULL,
    source VARCHAR(32) NOT NULL,      -- 'look_share'
    share_id INT NULL,
    created_at DATETIME_IMMUTABLE NOT NULL,
    INDEX idx_ref_inviter (inviter_id),
    INDEX idx_ref_invitee (invitee_id)
);
```

Запись — один раз после успешной регистрации при резолве `look_share_ref` из сессии. Награды/лимиты за приглашения — вне MVP, отдельный спек «Реферальная программа».
