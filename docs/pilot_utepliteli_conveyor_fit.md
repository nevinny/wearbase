# Пилот utepliteli.org на grounded-конвейере WEARBASE — оценка BD

**Дата:** 2026-07-19
**Тип:** read-only анализ под первый платящий пилот движка. Ничего не менялось ни в одном из проектов.
**Проекты:**
- Клиент: `/Volumes/SAMSUNG-origin/Users/zyablik/work/newutepliteli` (сайт utepliteli.org, тематика — утеплители/теплоизоляция/стройматериалы).
- Движок: `/Volumes/SAMSUNG-origin/Users/zyablik/work/wearbase` (RAG-конвейер discover→fetch→embed→generate).

## TL;DR (вывод первым абзацем)

Пилот **уже наполовину подключён** — и это главный факт для BD. Клиент работает на **идентичном стеке** (Symfony 7.4 / PHP 8.2 / Doctrine / EasyAdmin 4 / **MySQL 9.1**, тот же, что у wearbase) и уже интегрирован с продуктизированным сиблингом конвейера — проектом **`seo-factory`** (`~/work/seo-factory`) — через REST `POST /api/rewrite/batch` (команды `app:tn:fetch-nav`, `app:tn:rewrite-content`). **42 из 268 товаров уже прошли grounded-рерайт** с анти-плагиатным гейтом (`SourceSimilarityGuard`). Домен для граундинга **исключительно фактурный** (числовые характеристики: теплопроводность λ, плотность кг/м³, группа горючести, паропроницаемость, ГОСТ/ТУ) — низкий риск галлюцинаций, гейт применим. Продуктовый рерайт лёг как есть; незакрыты **категорийные гайды, сравнения материалов, FAQ и schema.org JSON-LD** — именно то, что умеет `LlmService` (generateGuide / generateListicle / generateBrandFaq), но чего клиент ещё не заказывал. Это и есть тело платного пилота.

## 3. Источники для граундинга

Домен **очень фактурный** — лучший из возможных для grounded-подхода:
- **Собственная БД:** `specs` (198 товаров) + `product_params` (1351) — числовые характеристики, которые нельзя выдумывать и легко проверять.
- **Официальный первоисточник производителя:** уже собирается командой `app:tn:fetch-nav` с `nav.tn.ru` (+ PDF тех.листы) в `var/tn_corpus.json` — обход антибота shop.tn.ru через браузер. Это «эталон истины» для минеральной изоляции ТЕХНОНИКОЛЬ.
- **Нормативы (ГОСТ/СНиП/СП):** упоминаются в инструкции рерайта, но **в БД их нет** — для авторитетных «как выбрать»-гайдов понадобится небольшой курируемый корпус норм (SP 50.13330, ГОСТ 9573 и т.п.).

Риск галлюцинаций **низкий**: числа берутся из фактов, инструкция уже жёстко требует «сохрани ВСЕ числовые характеристики точно; чего нет в фактах — не упоминай».

## 4. Что уже построено на стороне клиента (важнейший контекст пилота)

Клиент **не green-field** — интеграция с движком идёт:

- **`app:tn:fetch-nav`** — сбор корпуса-источника с nav.tn.ru → `var/tn_corpus.json`.
- **`app:tn:rewrite-content`** — grounded-рерайт: собирает корпус из БД (`description`+`specs`+`params`), шлёт пакетом на **seo-factory** `POST /api/rewrite/batch` с `{project, items:[{externalRef, title, targetKeyword, contentType, customInstruction, sources:[{url, sourceType, text}]}]}`, polling `GET /api/rewrite/batch/{id}`, пишет назад в `description`/`anons`/`meta*` с провенансом. Есть режимы `--push-to` (на 2-й сайт), `--avoid-current` (антидубль между своими сайтами), `--dry-run`, `--resume`.
- Env клиента: `SEO_FACTORY_URL=http://seo-factory.dev.local`, `INTAKE_API_TOKEN=…`.

**seo-factory** (`~/work/seo-factory`, команды `CreateUser`, `ExpandKeywords`, `RunSite`) — это **продуктизированный вынос RAG-конвейера wearbase в отдельный мультипроектный сервис** (поле `project` в API, per-project наборы текстов). Т.е. монетизационный движок уже существует в зачаточном виде, а utepliteli — фактически его первый интеграционный клиент. Для BD-нарратива: пилот продаёт не «интеграцию с нуля», а **расширение уже работающего контракта** на новые типы контента.

## 5. Маппинг на конвейер (`LlmService` + гейты)

`LlmService` — generic string-in/out. Доменная привязка живёт **в промптах** (хардкод «бренд одежды», «streetwear», женщина-кураторка, «чем заменить X в России»), **не в сигнатурах**. Сигнатуры оперируют абстракцией `brands: [{name, city, facts}]` = «сущность + проверенные факты», которая один-в-один ложится на «материал/товар + specs». seo-factory уже снял доменную связку, вынеся `customInstruction` в параметр API (клиент шлёт свой доменный промпт — для товаров это уже сделано).

| Деливерабл | Метод движка | На чём граундится | Статус фита |
|---|---|---|---|
| Grounded-описания товаров | rewrite-путь (customInstruction) | `specs`+`params`+корпус nav.tn.ru | **Работает** (42 готово) |
| Категорийные гайды «как выбрать утеплитель для фасада/кровли/пола» | `generateGuide` (nicheTitle=категория, «brands»=товары/материалы) | агрегат `specs` товаров категории + корпус норм ГОСТ/СНиП | Нужна доработка |
| Сравнение материалов «минвата vs XPS vs PIR» | `generateListicle` + `comparisonBlockRule` (markdown-таблица уже есть) | `specs` по разным категориям | Нужна доработка |
| FAQ по монтажу/характеристикам + FAQPage JSON-LD | `generateBrandFaq` (фразы Wordstat + факты) | `specs` + нормы | Нужна доработка |
| Листиклы «ТОП утеплителей для X» / «чем утеплить Y» | `generateListicle` (+ ItemList JSON-LD) | `specs` товаров ниши | Нужна доработка |
| schema.org JSON-LD (Product/Article/ItemList/FAQPage) | эмиттеры на стороне деливерабла | сгенерированный контент | Нужна доработка (у клиента вся Фаза 1 ⬜) |

**Гейты качества:**
- `BrandRagService` gate (chunks≥3 И score≥0.5) — **менее релевантен**: факты берутся из собственной БД (`specs`), а не ретривятся из веб-корпуса, так что «мало чанков» тут не проблема.
- `SourceSimilarityGuard` (анти-плагиат против источника) — **это и есть ключевой применимый гейт**, уже подключён; именно он закрывает претензию ТЕХНОНИКОЛЬ о копировании контента.
- Критичный доменный гард — **сохранность чисел** (λ, плотность, горючесть): уже прописан в инструкции; при масштабировании стоит добавить пост-проверку «все числа источника присутствуют в выводе».

**Где ляжет как есть:** транспорт (REST batch API), grounded-рерайт товаров, анти-плагиат, идентичный стек (Symfony/Doctrine/EasyAdmin/MySQL 9.1), провенанс + защита ручных текстов.

**Где нужна доработка:** (a) доменные промпты для гайдов/FAQ/сравнений (по образцу уже вынесенного `customInstruction`); (b) агрегация `specs` по категории + инъекция корпуса норм; (c) Twig-эмиттеры JSON-LD у клиента; (d) ключевики домена «утеплители» (в wearbase есть `KeywordService`/Wordstat, в seo-factory — `ExpandKeywords`); (e) группировка товар↔категория.

## 6. Оценка пригодности домена

**Высокая.** Утеплители — один из самых фактурных доменов: почти каждое утверждение сводится к нормируемому числу (теплопроводность, плотность, горючесть, паропроницаемость, прочность, размер, ГОСТ). Это:
- минимизирует галлюцинации (нечего «досочинять» — либо число есть в фактах, либо блок пропускается);
- делает анти-плагиатный гейт осмысленным и достаточным;
- даёт естественные GEO/AI-Overview-ответы (числовой ответ на «какая теплопроводность у X» — идеальный сниппет).

Единственная оговорка: тонкий каталог (9 брендов / 268 товаров) — часть категорий может содержать мало товаров, гайды там будут короткими; перед POC стоит замерить кол-во товаров на топ-категорию.

## 7. Дешёвый POC (что бы вошло)

**Scope:** 8–10 grounded **категорийных гайдов** на топ-категории (Теплоизоляция, Утепление фасадов, Кровельные материалы, Звукоизоляция, Минеральная вата, Базальтовый утеплитель, Экструзионный пенополистирол, PIR-плиты) + **FAQ** (5–6 Q&A на гайд) + **schema.org** (Article + FAQPage + ItemList) + добивка **31 пустого описания категорий**.

**Факты:** агрегат `specs` товаров каждой категории (198 товаров с характеристиками уже в БД) + маленький курируемый фактлист ГОСТ/СНиП. Ключевики — через Wordstat (`ExpandKeywords` в seo-factory).

**Почему лучше текущего:**
- сегодня 31/42 категорийных страниц **вообще без текста** — POC закрывает дыру осмысленным контентом;
- контент **grounded** (числа не выдуманы) и **анти-плагиат-гейтед** — снимает риск повторения претензии ТЕХНОНИКОЛЬ о копировании;
- поставляет **schema.org**, которую tasktracker клиента (Фаза 1: Product/Article/FAQPage) ещё даже не начинал → мгновенная GEO/rich-snippet-ценность;
- **переиспользует уже живой контракт** `/api/rewrite/batch` (добавить `contentType: guide|faq`), минимум нового кода на клиенте: команда «собрать корпус по категории» + Twig-блоки JSON-LD.

**Оценка кода:** новая клиентская команда `app:tn:generate-guides` (по образцу `RewriteContentCommand`, ~день); доменные промпты гайд/FAQ в seo-factory (полдня); Twig JSON-LD (полдня); курируемый корпус норм (полдня-день). Инфраструктура и транспорт готовы.

## 8. Честные препятствия

1. **`specs` — один неструктурированный TEXT-блоб**, не типизированные колонки. Для гайдов/FAQ парсится нормально (формат «показатель\nзначение»), но для **сравнительных таблиц с фильтрами** (λ, плотность, горючесть по колонкам) сначала нужна экстракция чисел в структурированные поля — иначе таблицы собираются только текстом из specs.
2. **Норм ГОСТ/СНиП нет в БД.** «Как выбрать»-гайды без них граундятся только на товарных specs (авторитетно про товар, слабее про методику выбора). Нужен небольшой курируемый корпус норм.
3. **Тонкий каталог** (9 брендов / 268 товаров) — часть категорий может дать короткие гайды; проверить товары-на-категорию до фиксации scope.
4. **Антибот shop.tn.ru** — сбор свежего корпуса требует браузерного обхода / nav.tn.ru (уже решено через `fetch-nav` + `var/tn_corpus.json`).
5. **Доменная связка движка в промптах wearbase** (fashion-хардкод) — но это уже обойдено в seo-factory через `customInstruction`; для новых деливераблов промпты пишутся заново под домен, плюмбинг не трогается.
6. **Группировка товар↔категория — через дерево `main`** (`entity_type_id`+`entity_id`+`parent_id`), у `product` нет `category_id` (есть только `brand_id` и `parent`). Для категорийных деливераблов нужен обход дерева / отдельный запрос группировки.
