# AirLLM — разбор и вердикт для нашего рига

> Ресёрч 2026-11-22. Источники: [GitHub lyogavin/airllm](https://github.com/lyogavin/airllm),
> [PyPI airllm](https://pypi.org/project/airllm/), [issues](https://github.com/lyogavin/airllm/issues),
> [разбор на dev.to](https://dev.to/arshtechpro/airllm-runs-a-70b-model-on-a-4gb-gpu-its-true-and-thats-not-the-interesting-part-hha).
> Цифры собраны из пересказов страниц, сырые страницы не сверялись.

## Вердикт

**Нам не нужна.** AirLLM позволяет *запустить* модель крупнее VRAM ценой скорости в секунды или
минуты на токен. У нас проблема в другом: генерация (`gemma4:26b`) уже целиком помещается в VRAM
и работает в нормальном темпе. Плюс у AirLLM узкое место — диск, а на риге свободно ~17–55 ГБ
(70B в FP16 весит ~140 ГБ, а нарезка по слоям ещё и дублирует веса).

## Что это

Python-библиотека для **послойного инференса**: модель один раз режется на слои и сохраняется
на диск. При генерации на GPU держится **один слой за раз**: загрузили, посчитали, выгрузили,
взяли следующий. Поэтому нужная VRAM зависит от размера слоя, а не от размера модели (по README
70B помещается в ~4 ГБ, 405B — в ~8 ГБ). Опционально есть prefetch следующего слоя (по README
работает только для Llama2) и сжатие весов 4/8 bit через bitsandbytes. Сжатие нужно, чтобы
быстрее читать с диска, а не ради экономии VRAM.

- Версия **4.0.0 от 05.09.2026**, релизы примерно раз в месяц. 114 открытых issues, новые
  появляются в ноябре 2026.
- Заявлены Llama 2–4, Qwen 1–3.x (включая MoE и VL), DeepSeek V2/V3/R1, Mistral/Mixtral, Gemma,
  Phi и др. На macOS работают только Llama-подобные архитектуры.
- API — только `model.generate()`. OpenAI-совместимого сервера и стриминга в README нет.
- Требуемая версия transformers различается по моделям (Kimi K3 — 4.56.x, Qwen3.8 — 5.8+).

## Скорость (главное)

Каждый токен требует прочитать **всю модель с диска**, поэтому скорость задаёт диск, а не GPU.

| Замер | Сек/токен |
|---|---|
| Release notes v3.1.0, RTX 6000 Ada (диск не указан) | **292** (+900 с инициализация) |
| Сообщения пользователей, NVMe | 5–35 |
| Батч из 50 промптов вместо одного | 35 → 5.3 (~6.6×) |
| Для сравнения: llama.cpp, квантованная 70B на RTX 4090 | 0.07–0.12 (8–15 ток/с) |

Расчёт автора dev.to для 70B FP16: Gen4 NVMe ~20 с/токен, SATA SSD ~280 с/токен. Описание бренда
на ~500 токенов заняло бы от **3 часов до 1,5 суток**.

## Известные проблемы (issues, ноябрь 2026)

- [#402](https://github.com/lyogavin/airllm/issues/402): нарезка дублирует веса на диске (2×),
  OOM на 8 ГБ при prefill с большим словарём, утечка KV-кэша.
- #396: память растёт O(n²) на длинных промптах (GQA, Windows).
- #404: на macOS/MLX падают модели с tied embeddings.

## Почему не подходит именно нам

| Ограничение рига (замеры `ssh llm`, окт. 2026) | Как бьёт по AirLLM |
|---|---|
| Диск: свободно ~17–55 ГБ | 70B FP16 ≈ 140 ГБ, плюс дубль при нарезке. Не помещается |
| Скорость диска | Определяет скорость генерации целиком |
| pypi.org с рига уходит в таймаут | `pip install airllm` напрямую не поставится |
| Суммарно ~44 ГБ VRAM на 6 картах | Модели до ~40 ГБ (квант) раскладываются по картам штатным offload в ollama/llama.cpp на порядки быстрее |
| CPU без AVX2 | Совместимость bitsandbytes и нативных колёс не проверена; ComfyUI на этом уже падал |

## Когда пересмотреть

Если понадобится **разовый офлайн-прогон** модели, которая не помещается даже в 44 ГБ VRAM
(например, 405B для генерации эталона или оценки качества на десятке примеров), и при этом будет
быстрый NVMe на сотни ГБ. Даже тогда сначала стоит сравнить с llama.cpp с частичным
CPU/GPU-offload квантованной версии. Для конвейера брендов (сотни генераций) AirLLM непригоден
в принципе.
