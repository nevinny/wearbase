# Гардероб: локальная vision-модель, которая учится на данных семьи

Статус: дизайн-док (2026-07-22). Реализация — по фазам ниже.
Контекст кода на момент написания: `src/Service/Wardrobe/WardrobeAiService.php`,
`LlmService::generateVision*` (`src/Service/LlmService.php`), сущность
`src/Entity/WardrobeItem.php`, переиспользуемая RAG-инфра
(`EmbeddingService`, `VectorStoreService`, `BrandRagService`).

---

## 0. TL;DR

**Фаза 1 (MVP, рекомендуется делать сейчас):** НЕ RAG и НЕ fine-tune. Дешёвая
детерминированная персонализация в промпте: (а) словарь категорий строим из
реальных подтверждённых `wardrobe_item.category` этого пользователя, (б) держим
append-only лог «что предложил AI → что пользователь оставил» и подмешиваем в
промпт систематические правки + 2-3 примера его собственных названий. Работает с
1-го сохранённого объекта, без GPU, без нового embedder, идёт на скромном Mac.
Одна новая таблица (`wardrobe_ai_feedback`), один новый сервис
(`WardrobePersonalizer`), точечная правка `analyzePhoto()`.

**Фаза 2 (позже, по триггеру):** текстовый RAG two-pass — эмбеддим подтверждённые
вещи и на новом фото подмешиваем k семантически ближайших примеров пользователя.
Переиспользует `EmbeddingService` как есть (текст!), новая Qdrant-коллекция.

**Fine-tune (LoRA/QLoRA):** для одной семьи — практически никогда. Данных на 1-2
порядка меньше нужного, риг операционно не тянет, налог на поддержку высокий.
Дверь оставляем, но триггер — порог данных (>~2000 сбалансированных правок +
доказанная визуальная ошибка, которую промпт не лечит), а не календарь.

## 1. Честный разбор развилки «дообучается на моих данных»

Формулировка неоднозначна. Есть три принципиально разные вещи, и наивная
«RAG по фото» упирается в модальность, которую надо назвать вслух.

### 1.1. Где именно «учение»? Сигнал в основном ТЕКСТОВЫЙ, не визуальный

Ключевое наблюдение: VLM и так **видит** фото. То, что она делает не так для
конкретной семьи, — это почти не «распознавание пикселей», а **лексика и
конвенции**:

- пользователь называет один и тот же крой «косуха», а модель — «куртка»;
- его таксономия категорий — из его реального шкафа («Ботильоны», «Ремни для
  сумок»), а не generic;
- его формат размера («46/M», а не «M»);
- стиль названия («Белая oversize футболка»).

Всё это — текстовые/категориальные поправки. Значит основной рычаг обучения —
**персонализация промпта из подтверждённых меток**, а не переобучение весов и не
визуальный retrieval. Это и делает Фазу 1 такой дешёвой.

### 1.2. Развилка А — Retrieval / few-shot (RAG). Разбор по модальности

Наивная идея из задачи: «эмбеддить фото + метки в Qdrant, на новом фото
подмешивать k ближайших». Проблема — **модальность эмбеддингов**:

- Имеющийся `EmbeddingService` — это **текстовый** embedder (qwen3-embedding:0.6b,
  1024-dim). Он не умеет эмбеддить картинку.
- Чтобы искать визуально-похожие прошлые вещи по НОВОМУ фото, нужен
  image/мультимодальный embedder (CLIP/SigLIP/jina-clip/nomic-embed-vision).
  ollama такое из коробки почти не отдаёт → это **новая инфра** с сомнительной
  окупаемостью для личного шкафа (см. 1.1: выигрыш в основном текстовый).

Отсюда две реализуемые версии RAG:

- **Text-RAG two-pass (реалистичный, Фаза 2):** Pass 1 — VLM даёт черновик
  `{category,name,...}`. Эмбеддим ТЕКСТ черновика (`category + name + notes`),
  достаём k ближайших **подтверждённых** вещей этого пользователя по тексту.
  Pass 2 — переспрашиваем VLM с блоком «похожие вещи из твоего шкафа и как они
  подписаны» как few-shot. Использует `EmbeddingService` без изменений
  (эмбеддим текст) + новую коллекцию Qdrant. Цена: 2 вызова VLM (латентность на
  Mac). Ограничение честное: retrieval по собственному черновику модели **не
  чинит ошибку, которую модель уже сделала на Pass 1** (garbage-in).
- **Image-RAG (Фаза 3, вероятно никогда):** визуальный embedder. Реальный выигрыш
  только если появятся визуальные различия, которые VLM путает системно и текст
  не спасает. Не строим спекулятивно.

Вывод: RAG — да, но как Фаза 2, и это **текстовый** RAG. Дефолт Фазы 1 — ещё
проще (детерминированный, без Qdrant).

### 1.3. Развилка Б — настоящий fine-tune (LoRA/QLoRA VLM). Почему нет

Конкретно, а не «дорого»:

- **Данных на 1-2 порядка меньше нужного.** QLoRA на 3-7B VLM реалистично
  требует сотни–низкие тысячи image-instruction пар, чтобы сдвинуть качество без
  переобучения. Семья за всю жизнь набьёт ~100-300 вещей, распределение
  длиннохвостое (в редких категориях 1-2 примера). Дата-голод.
- **Риг операционно не тянет.** CPU i7-2670QM (древний, 4C/8T), RAM/диск
  ограничены (модели ~20 ГБ не влезают), 4 потребительских GPU, IP непостоянен,
  LAN-only, делится с майнингом и RAG-конвейером. Шардить обучение VLM по 4
  картам с таким CPU — мучение; диск не держит крупные базы.
- **Налог на поддержку.** Каждый ретрейн → merge адаптера → конвертация в GGUF →
  переквантизация → перезаливка в ollama на Mac. Постоянные расходы без внятного
  выигрыша.
- **Риск catastrophic forgetting** и деградации русского/JSON на маленьком
  датасете.

**Порог пересмотра (а не дата):** только если одновременно (а) накопилось
>~2000 исправленных, классово-сбалансированных примеров, И (б) есть КОНКРЕТНАЯ
устойчивая визуальная ошибка, которую персонализация промпта доказуемо не лечит.
Для одной семьи — считать «никогда»; дверь открыта, триггер — данные.

### 1.4. Развилка В — гибрид / feedback-loop (это и есть план)

- **Сбор сигнала как ground truth:** сейчас черновик AI показывается в UI и
  **теряется** при сохранении. Пользователь правит подсказку перед save — это
  и есть разметка. Надо её ловить: снимок `ai_suggestion` в момент сохранения +
  финальные поля вещи → append-only `wardrobe_ai_feedback`. Это единственный
  новый write-путь.
- **Персональность (владелец vs супруга):** сигнал строго per `user_id`. Вещи
  уже принадлежат пользователю (`WardrobeItem.user`). Правки и retrieval
  скоупятся по `user_id` (WHERE / payload-фильтр в Qdrant). Общий стор с
  фильтром, а не раздельные коллекции — проще и хватает.
- **Холодный старт (3-уровневый fallback):** у пользователя <N подтверждённых
  вещей → падаем на household-уровень (объединённый словарь семьи) → падаем на
  статические `WardrobeItem::SUGGESTED_CATEGORIES`. Никакой «пустой»
  персонализации: без истории поведение = сегодняшнее.

## 2. Рекомендация по фазам

### Фаза 1 — детерминированная персонализация промпта (MVP)

Что: перед vision-вызовом собрать для `$user`:
1. **Словарь категорий** = топ реально используемых `wardrobe_item.category`
   пользователя (по частоте, `deleted_at IS NULL`) ∪ статический список. Вставить
   вместо жёсткого `implode(', ', SUGGESTED_CATEGORIES)` в `analyzePhoto()`.
2. **Блок систематических правок** = из `wardrobe_ai_feedback` пары, где
   `ai.category != final.category` (или size), повторяющиеся **≥2 раз**
   → строка «Раньше для похожего ты исправлял: 'куртка'→'косуха'». Порог ≥2
   защищает от переобучения на единичном каприз-эдите.
3. **Few-shot названий** = 2-3 последних подтверждённых `name` пользователя как
   пример стиля именования.

Триггер завершения Фазы 1: метрика «доля полей, которые пользователь правит
после подсказки» замерена (можно из того же `wardrobe_ai_feedback`). Если
остаточная ошибка высокая и она **семантическая по категориям** — идём в Фазу 2.

### Фаза 2 — текстовый RAG two-pass (по триггеру)

Триггер: у активных пользователей ≥~30-50 подтверждённых вещей И глобальные
правки Фазы 1 слишком грубые (много редких категорий, где «топ-N словарь» их не
покрывает). Механика — 1.2 (Text-RAG two-pass). Gate качества по образцу
`BrandRagService`: подмешиваем few-shot только если нашли ≥2 примера со score
≥ порога, иначе работаем как Фаза 1 (без второго вызова — экономим латентность).

### Фаза 3 / fine-tune

Не планируется. См. 1.2 (image-RAG) и 1.3 (fine-tune) — оба за порогом данных.

## 3. Какую vision-модель брать локально

Требование: локальный VLM, стабильный русский, JSON, скромное железо. Приватность
= инференс не уходит в облако; для супруги — предпочтительно **на её Mac**
(on-device), т.к. риг LAN-only и у владельца.

### Mac супруги (скромное железо, без мощного GPU) — основной путь

- **Дефолт: `gemma3:4b`** (мультимодальный, сильный мультиязычный/русский, влезает
  в скромную RAM Q4 ~3-4 ГБ). Лучший баланс «влезает + русский + JSON» для
  слабого Mac.
- **Если Apple Silicon с ≥16 ГБ: `qwen2.5vl:7b`** — заметно лучше по
  атрибутам/OCR бирок, но тяжелее.
- Избегать moondream (слабый русский) и 11B+ vision (llama3.2-vision:11b) на
  слабом Mac — не влезет/медленно.
- Замечание по инфре: на dev-Mac ollama уже стоит (`/usr/local/bin/ollama`), но
  vision-модель не скачана (есть только qwen3:8b, qwen3-coder). На Mac супруги —
  поставить ollama и `ollama pull gemma3:4b`. **Перед pull проверить свободную
  RAM/диск.**

### Риг (4 GPU, LAN-only, RAM/диск ограничены) — НЕ основной путь

- Может крутить `qwen2.5vl:7b` или VLM класса ~32b, если влезает в одну карту.
- Но: LAN-only, у владельца, делится с майнингом/RAG, IP непостоянен. Делать
  ежедневный путь супруги зависимым от рига **нельзя**. Риг — для батч-задач
  (эмбеддинг Фазы 2, любой маловероятный training), не для интерактивного
  инференса супруги.

### JSON на русском — усиление надёжности (опционально, точечно)

Маленькие VLM (3-4B) дают более хрупкий JSON. `extractJson()` терпим, но стоит
добавить в `generateVisionLocal()` ollama `format: "json"` (structured output) —
маленькая хирургическая правка, ощутимо снижает битый JSON. Это единственная
уместная правка `LlmService`.

## 4. Модель данных

### 4.1. Новая таблица `wardrobe_ai_feedback` (Фаза 1) — ЕДИНСТВЕННОЕ обязательное добавление

Причина: сырой черновик AI сейчас нигде не персистится. Ловим (снимок подсказки)
↔ (что пользователь оставил).

Поля (append-only, без физического delete):

| Поле | Тип | Назначение |
|---|---|---|
| `id` | INT PK AI | |
| `user_id` | INT NOT NULL, FK→`user.id` | `User.id` — plain INT (не unsigned), FK без 3780 |
| `wardrobe_item_id` | INT NULL, FK→`wardrobe_item.id` ON DELETE SET NULL | вещь может быть soft-deleted позже |
| `photo_hash` | CHAR(40) NULL | sha1 фото (тот же ключ, что в кеше); НЕ храним байты |
| `ai_json` | JSON | снимок подсказки AI в момент сохранения |
| `final_json` | JSON | финальные поля вещи (category/name/size/notes) |
| `source` | VARCHAR(20) | web/telegram/import (как `WardrobeItem::SOURCE_*`) |
| `created_at` | DATETIME | |

- Индекс `(user_id, created_at)` — выборка последних правок пользователя.
- Миграция: `CREATE TABLE IF NOT EXISTS`, имя вида
  `Version2026XXXX_wardrobe_ai_feedback.php`. Никакого `schema:update`.
- Приватность: храним хеш и JSON-метки, **не** байты фото (фото уже лежит в
  `wardrobe_item.photo` через Vich). В облако не уходит ничего (см. §6).

Словарь категорий Фазы 1 отдельной таблицы НЕ требует — считается запросом по
`wardrobe_item` (репозиторий `WardrobeItemRepository`).

### 4.2. Qdrant-коллекция `wardrobe_items` (Фаза 2)

- Отдельная коллекция (НЕ `brand_chunks`). 1024-dim, Cosine — как у текущей.
- Payload: `{user_id, item_id, category, name, size, notes}`.
- Payload-index на `user_id` (иначе фильтр = full scan, ср. index на `brand_id`).
- Эмбеддим ТЕКСТ вещи (`category + name + notes`) через `EmbeddingService.embed()`
  без изменений.
- ⚠️ `VectorStoreService` жёстко завязан на `brand_chunks`/`brand_id`
  (конструктор + все методы `*ByBrand`). НЕ перегружать его brand-семантику.
  Сделать тонкий сиблинг-сервис (напр. `WardrobeVectorStore`) с
  `upsertItem/searchByUser(user_id, vector, k)` — ~40 строк по образцу, чище чем
  впихивать user_id в brand-методы. DI-инстанс с коллекцией `wardrobe_items`.

## 5. Точки интеграции (хирургические)

Все правки — no-op при `$user === null` или пустой истории → сегодняшнее
поведение сохраняется бит-в-бит.

1. **Новый сервис `WardrobePersonalizer`** (`src/Service/Wardrobe/`):
   - `categoryVocabulary(User $user): array` — топ-категории пользователя ∪
     `SUGGESTED_CATEGORIES` (fallback household → static).
   - `promptBlock(User $user): string` — блок правок (≥2 раз) + few-shot названий;
     '' если истории нет.
   - `recordFeedback(User $user, array $aiFields, WardrobeItem $final): void` —
     запись в `wardrobe_ai_feedback`.

2. **`WardrobeAiService::analyzePhoto()`** (строки ~119, ~141):
   - `$categories = implode(', ', $this->personalizer->categoryVocabulary($user))`
     вместо статического списка.
   - дописать `$prompt .= $this->personalizer->promptBlock($user);`
   - проброс `$user` уже есть в сигнатуре.

3. **`WardrobeController` (save-экшен)** и `WardrobeIngestController` (telegram):
   в момент сохранения вещи вызвать `personalizer->recordFeedback(...)`. Черновик
   AI для сравнения прокинуть из сессии/скрытого поля формы (сейчас теряется — это
   и есть недостающий кусок). `FamilyController` — только если он тоже сохраняет.

4. **Кеш-ключ** (`WardrobeAiService::suggestFromPhoto`, строка ~62): сейчас ключ =
   `wardrobe_ai_photo_{sha1(photo)}` — **общий для всех пользователей**. С
   персонализацией это баг (супруга получит подсказку под словарь владельца, если
   сфоткали одну вещь). Добавить в ключ `user_id` и грубый счётчик истории
   (напр. число вещей пользователя / 10), чтобы кеш инвалидировался по мере
   накопления данных. Минимальная, но обязательная правка.

5. **Config / env** (`config/services.yaml` ~143, `.env`):
   - опционально ввести `WARDROBE_LOCAL_LLM_URL` (default = `LOCAL_LLM_URL`),
     чтобы vision супруги мог указывать на **её localhost ollama**, независимо от
     RAG-рига. Сейчас `WARDROBE_VISION_LOCAL=1` в `.env.local` гонит vision на риг
     (192.168.0.111) — для on-device приватности супруги это надо развязать.
   - `WARDROBE_VISION_LOCAL` и OpenRouter-fallback не трогаем (см. §6).

6. **Опционально `LlmService::generateVisionLocal()`** (строка ~193): добавить
   `'format' => 'json'` в тело запроса ollama для надёжного JSON у маленьких VLM.

## 6. Уживчивость с `WARDROBE_VISION_LOCAL` и запасным OpenRouter

- Переключатель остаётся ровно как есть: `1` = локальная ollama (риг или, по
  рекомендации, Mac супруги через `WARDROBE_LOCAL_LLM_URL`), `0` = облачный
  OpenRouter (`WARDROBE_VISION_MODEL=google/gemini-2.5-flash-lite`).
- **Обучение/персонализация — НИКОГДА не в облаке.** Это тривиально соблюдается:
  Фаза 1 и 2 — локальные (SQL + локальный embedder + локальный VLM); fine-tune
  (если бы был) — только риг. Облако участвует лишь как ручной аварийный vision-
  инференс, и туда уходит только одно фото по явному флагу.
- Персонализация промпта модель-агностична: тот же `promptBlock`/словарь работает
  и при `LOCAL=0` (OpenRouter) — но фото семьи туда слать не по умолчанию, флаг
  оставить `1`.
- Text-RAG Фазы 2 требует локального embedder (риг/Mac). При `LOCAL=0` без
  доступного embedder — просто деградируем в Фазу 1 (gate не находит примеров).

## 7. Риски

1. **Ценность retrieval vs латентность (Фаза 2).** Text-RAG ищет по собственному
   черновику модели → не чинит ошибку Pass 1, а второй VLM-вызов на слабом Mac
   удваивает ожидание ради маржинального выигрыша над дешёвой Фазой 1.
   *Митигация:* Фазу 2 включать только по замеренной остаточной ошибке Фазы 1;
   gate по score/кол-ву примеров, иначе не делать второй вызов.
2. **Мало, несбалансированно, дрейф.** Длинный хвост категорий с 1-2 примерами;
   few-shot/правки могут переобучиться на единичный каприз-эдит.
   *Митигация:* инжектить правку только при повторе ≥2; лимит few-shot; статический
   словарь как якорь; порог ≥N вещей для household/personal уровней.
3. **JSON/русский у маленького локального VLM.** 3-4B слабее облачного
   gemini-flash-lite: битый JSON, галлюцинации полей, хуже OCR бирок.
   *Митигация:* `format:"json"` в ollama; выбор gemma3:4b/qwen2.5vl:7b (лучший
   малый мультиязычный); ручной OpenRouter-фолбэк остаётся.
4. **(доп.) Зависимость от рига.** RAM/диск лимит, IP скачет, LAN-only, делится с
   майнингом/RAG. *Митигация:* ежедневный путь супруги — на её Mac-ollama, риг
   только для батчей.
5. **(доп.) Приватность через кеш/логи.** *Митигация:* в кеше только хеш; в
   `wardrobe_ai_feedback` только JSON + ссылка на вещь, не байты; в OpenRouter —
   ничего без явного флага.
