# 4× Tesla V100 SXM2 + NVLink — выводы из видео-обзора (2026-09-24)

Источник: расшифровка русскоязычного YouTube-обзора (`v100-nvlink-transcript.txt` в корне репо, не закоммичен).
Автор 3,5 недели собирал и тестировал самодельный «DGX»: 4× V100 SXM2 16 ГБ на китайской
плате с NVLink, водянка; сравнивал с арендованными 4× V100 32 ГБ (с NVLink и без, через PCIe) и 2× RTX 3090.
68 конфигураций, 13 LLM, 8 моделей для картинок, 2 для видео.

**Главный вывод:** лишние карты дают не скорость, а **память под KV-кэш/контекст**. 2→4 карты:
+34 % ток/с, но контекст 26K → 440K (×17). Для LLM от 14B+ сборка за ~180 тыс. ₽ лучше пары 3090;
для генерации видео проигрывает в 4–5 раз, для картинок — ничья (кроме Qwen-Image).

## Цифры

| Что | Результат |
|---|---|
| Gemma 3 12B Q4 GGUF, 4 карты: LM Studio / llama.cpp / vLLM (форк под Volta, TP) | 63 / 66 / **107** ток/с |
| Конвейерный режим (pipeline, llama.cpp) vs тензорный (TP, vLLM) | 32 vs 70 ток/с (~×2) |
| Плотная 27B: 1 карта 16 ГБ / 2 карты TP / 4 карты TP | OOM / 52 ток/с, 26K ctx / 70 ток/с, 440K ctx |
| 14B: 1 → 4 карты | 63 → 116 ток/с; контекст 22K → 273K |
| MoE 35B (~3B активных) | 115 ток/с — быстрее плотной 27B; KV-кэш 710K (TP) / 1,2M (гибрид 2×2) |
| 4 параллельных запроса | ~200 → ~700 ток/с суммарно (почти линейно, decode упирается в чтение весов) |
| Без NVLink (PCIe) | −10 % на 1 карте, −12 % на 2, **−25 % на 4**; TP/pipeline-разрыв сжимается с ×2 до ×1,5 |

| vs 2× 3090 (TP) | 3090 быстрее до 14B (+13 % на 4B), дальше V100 впереди (−25 % у 3090 на 27B) — у 3090 без моста обмен идёт через RAM (~6 ГБ/с) |
| 8 из 10 моделей на 2× 3090 (48 ГБ) | упёрлись в свой обученный контекст (262K), а не в память |

## Грабли, полезные вне этого железа

1. **Open WebUI по умолчанию режет прикреплённый файл на чанки и отдаёт модели 3–4 фрагмента** (RAG),
   а не весь текст. Для длинного контекста включить «обход встраивания и извлечения»; проверять
   по заполнению KV-кэша в логе сервера, а не на глаз.
2. **Скорость ничего не значит, пока не прочитан ответ**: Qwen 3.8 4-bit на 2 картах TP выдавал
   зацикленный мусор (паддинг размерности слоя 4120→4128 проверен авторами только для TP=4);
   повторилось на двух независимых стендах.
3. **Бэкенд внимания в vLLM выбирается перебором**: из 4 один падает, один не работает, 75 vs 107 ток/с у оставшихся.
4. **Нет BF16 у Volta** → модели, обученные на BF16 (Qwen-Image), переполняются в FP16 → «чёрный квадрат»
   без ошибок в логах. Лечится эмуляцией BF16 (×3 медленнее). Проверять латенты до VAE.
5. **Квантованный text-encoder/коннектор в LTX** → модель игнорирует промпт (рисует «рыцаря» на любой запрос).
   Опасно сжимать именно мост «текст→латент», а не языковой блок целиком.
6. **Один процесс ComfyUI держит ~21 ГБ копии весов в системной RAM**; 4 экземпляра → 80 ГБ.
   Лечится флагом, запрещающим офлоад (веса живут только в VRAM).
7. Одну картинку/кадр несколько карт не ускоряют (последовательные шаги); выигрыш — только
   N независимых экземпляров = пропускная способность.
8. «Если чего-то нет, подожди»: 20 часов патчей форка vLLM, а через неделю вышла версия с исправлениями.
9. Перед покупкой железа арендовать ту же конфигурацию на пару часов (посекундная тарификация, ~1000 ₽).

## Применимость к нашему ригу (см. [llm_infra_handoff.md](llm_infra_handoff.md))

- Наш стек (ollama = llama.cpp) при дроблении модели работает **только в pipeline-режиме**; при нём
  на границе карт на каждый токен передаётся лишь вектор скрытого состояния, поэтому PCIe x1 почти не
  бьёт по генерации. ⚠️ Цифра «~13 ток/с на 5 картах» из §2.1 handoff — это `gemma4:31b` с CPU-офлоадом
  (13/61 слоёв на GPU), а не штраф за сплит: `gemma4:26b` на тех же 5 картах даёт 39 ток/с (замер ниже).
  TP (как vLLM+NVLink в видео) на x1 бессмыслен.
- Прямой вывод для генерации контента: **MoE-модели с ~3B активных параметров быстрее плотных
  26–27B при сопоставимом размере**. `gemma4:26b` (наш победитель в [model-ab-bench.md](model-ab-bench.md)) —
  при выборе замены смотреть на MoE, влезающие в одну A4000.
- **Параллельные запросы почти бесплатны** (decode ограничен чтением весов) — батчевый
  `generate-content` выгоднее гнать с `OLLAMA_NUM_PARALLEL` > 1, если хватает VRAM под кэш. Не
  проверено на нашем риге — замерить перед включением.
- Видео-ген локально: подтверждается вывод памяти про Seedance/Wan — нужен
  Ampere+ (BF16), и даже тогда критична системная RAM (энкодер LTX ~29 ГБ RAM). У нас 7,6 ГБ — не вариант.
- Если когда-то апгрейдить риг под LLM: 4× V100 SXM2 16 ГБ + NVLink-плата ≈ 180 тыс. ₽ (цены 09.2026:
  модуль 16 ГБ ~12–14,5 тыс. ₽, 32 ГБ ~60–80 тыс. ₽, плата на 4 карты ~72 тыс. ₽ с пошлиной).
  Но потребуется другой хост: плате нужен CPU/RAM (ComfyUI, офлоад), 200 Вт в простое, 1,35 кВт в пике,
  низкая ликвидность и неделями возни. Модули SXM2 не проверить без платы — брать только у продавцов с проверкой.

## Живая раскладка на риге (замер 2026-09-24, `ollama ps` + `nvidia-smi`)

ollama.service: `OLLAMA_NUM_PARALLEL=1`, `OLLAMA_CONTEXT_LENGTH=8192`, `OLLAMA_KEEP_ALIVE=-1`,
`CUDA_VISIBLE_DEVICES` = все 5 карт; flash attention и квант KV-кэша не включены.
`gemma4:26b` Q4_K_M занимает 19,0 ГБ VRAM (ctx 8192) — в одну A4000 (16 ГБ) не влезает, и ollama
размазала её **по всем пяти картам**:

| GPU | Карта | Занято |
|---|---|---|
| 0 | RTX 2060 SUPER | 5,1 / 8 ГБ |
| 1 | RTX 2060 SUPER (мёртвый вентилятор) | 3,6 / 8 ГБ |
| 2 | RTX A4000 | **6,3 / 16 ГБ** |
| 3 | CMP 30HX | 2,6 / 6 ГБ |
| 4 | CMP 30HX | 2,8 / 6 ГБ |

4 границы pipeline-передачи по PCIe x1, самая быстрая карта загружена на 40 %. `flash_attn = auto`.
Load с диска ~106 с, mmap ollama отключает «due to host memory pressure».

### Замеры (харнесс `~/llmbench/bench.py` на риге, лог всех настроек — `~/llmbench/results.jsonl`)

Промпт ~2,8K токенов (реальный размер промптов конвейера 2–3,2K), nonce в начале, temp 0, seed 42,
num_predict 400, ctx 8192; 1 прогрев + 3 прогона. Пишется env сервиса, VRAM/лимиты мощности/клоки/температуры
по картам до и после, RAM, строки загрузки из journal, начало ответа.

| A4000 + 2060S#0 | **527** | **53,7** | 11,3 с |
| A4000 + 2060S#0 + CMP | 526 | 53,5 | 11,1 с |
| A4000 + 2060S#0 + 2060S#1 | 526 | 53,5 | 11,7 с |

| A4000 + 2060S#0, `OLLAMA_FLASH_ATTENTION=1` | 527 | 53,6 | 11,2 с |
| A4000 + 2060S#0, `OLLAMA_FLASH_ATTENTION=0` | 276 | 50,8 | 18,0 с |
| 5 карт, `num_batch` 1024 / 2048 | 377 / 354 | 39,3 / 38,1 | 15,1 / 15,5 с |
| A4000 + 2060S#0, `num_batch` 1024 | 526 | 53,4 | 11,6 с |

Выводы перебора (`~/llmbench/sweep.log`, 2026-09-24):
- **Тормозят CMP 30HX, а не число карт.** Третья карта-2060S к паре A4000+2060S не стоит ничего; любая
  CMP в цепочке роняет prefill вдвое (276 против 527). Для `gemma4:26b` оптимум — A4000 + 2060S#0, +37 % decode.
- Flash attention: `auto` уже включает её (= FA1); выключение режет prefill вдвое. Трогать не нужно.
- `num_batch` выше дефолта ничего не даёт (2048 даже хуже). Квант KV и `NUM_PARALLEL` — отозваны (см. ниже).
- Остальное из видео (NVLink, tensor parallel vLLM, split-mode row) к ollama по PCIe x1 неприменимо.

### Смена моделей 26b ↔ 31b (`~/llmbench/sweep2.sh`, 2026-09-24)

`gemma4:26b` (19 ГБ) и `gemma4:31b-it-qat-mmap` (~22 ГБ VRAM на 5 картах) **вместе не живут**, а подгрузка
31b при резидентной 26b ломает сервис: на 5 картах warmup висел 30 мин до таймаута, на A4000+2060S#0 —
OOM-kill по `MemoryMax=6G`. Значит, двухкарточная раскладка годится только если на риге одна модель.

⚠️ **Боевая модель — не 26b.** В Mac `.env.local`: `LOCAL_LLM_MODEL` и `WARDROBE_OUTFIT_LOCAL_MODEL` =
`gemma4:31b-it-qat-mmap` (CLAUDE.md и `services.yaml` говорят `gemma4:26b`). Все 94 запроса с Mac за 2 дня —
31b. При этом кто-то локальный на риге (127.0.0.1, 2026-09-25 04:29 UTC, не найден) грузит 26b с
`KEEP_ALIVE=-1` → следующий батч с Mac попадает в сценарий смены моделей выше.

### OOM-kill посреди батча: кэш промптов llama-server (2026-09-25 02:09 UTC)

ollama 0.33.2 запускает `llama-server` с дефолтным **prompt cache в RAM на 8192 МиБ** (в логе: «prompt cache is
enabled, size limit: 8192 MiB»). Каждый промпт ~465 МиБ оседает в памяти хоста; на 7,6 ГБ RAM и
`MemoryMax=6G` через ~7 запросов с Mac — OOM-kill (запрос вернул 500, `llm-mem.log`: llama RSS 6190 МБ).
Фикс — выключить кэш через env, который `llama-server` читает сам (`LLAMA_ARG_CACHE_RAM`, см. `--help`):
drop-in `docs/llmbench/40-prompt-cache.conf` → `/etc/systemd/system/ollama.service.d/`. Промпты конвейера
разные (общий только системный), выигрыш кэша мал.

Медленный кластер 10–15 ток/с в journal за 15–24.09 — это другие модели (`gemma4:31b-it-qat-mmap`
с CPU-офлоадом), не `gemma4:26b`.

⚠️ **Не менять опции раннера (`num_batch`, `num_ctx`, `num_gpu`…) на живом сервисе**: ollama грузит
вторую копию модели рядом со старой → `MemoryMax=6G` → OOM-kill (проверено 2026-09-24 13:32, systemd
перезапустил сам, хост жив). Каждый вариант — только через чистый `systemctl restart`
(скрипт `~/llmbench/sweep.sh`, нужен sudo; сам возвращает исходный `20-tuning.conf`).

Отозвано: `OLLAMA_KV_CACHE_TYPE=q8_0` (KV-кэш и так ~0,5 ГБ суммарно — экономить нечего) и
`OLLAMA_NUM_PARALLEL>1` (конвейер шлёт запросы последовательно; комментарий в `20-tuning.conf` —
4 слота раздували VRAM и приводили к OOM 07.09).
