# План 2. Обработка и подготовка вещей для AI-стилиста

Дата: 2026-09-13. Статус: план реализации, код не изменён.
База проверки: `origin/main` (`b9b65f3`).
Потребитель результата: [ежедневные AI-образы](wardrobe_daily_outfits_plan.md).

## Цель и пользовательский сценарий

Пользователь загружает фото вещи или пачку фотографий, выбирает владельца гардероба,
видит результат распознавания и исправляет сомнительные поля. После подтверждения
вещь имеет достоверные атрибуты и пригодное для коллажа изображение.
Уже загруженные вещи проходят тот же процесс обогащения без потери ручных правок.

Разделить готовность данных для подбора и качество изображения для презентации:
стилист может работать по подтверждённым атрибутам до завершения удаления фона.

## Что уже есть и где разрыв

- `WardrobeIngestController`, `WardrobeItemDraft`, `IngestWardrobeDraftsCommand`:
  пакетная загрузка, SHA-256 дедуп одинаковых байтов, DB lease, processing,
  повторные попытки и защита от записи результата устаревшего worker.
- `WardrobeDraftPromotionService`: подтверждение с блокировкой, идемпотентность,
  привязка к владельцу и перенос фото в карточку.
- Приватная выдача фото через проверку семейного доступа.
- `WardrobeAiService::normalizePhotoFields` складывает цвет, материал, сезон и крой
  в `notes`; promotion переносит название, категорию, размер и заметки.
  Подбор читает `colorName`, `materialText`, `season`, `styles` отдельно.
  Поэтому успешно распознанное фото ещё не гарантирует пригодные данные для стилиста.

## Этапы

### 1. Сохранить распознанные атрибуты в нужные поля — первый приоритет

Расширить контракт результата распознавания и черновика структурированными полями:
категория, цвет, сезон, материал, фасон и предлагаемые стили.
Переиспользовать существующие поля `WardrobeItem` и справочник стилей.
Функциональную роль для подбора определять по нормализованной категории;
отдельный справочник вводить только если текущие категории не позволяют однозначный маппинг.

Передавать поля через worker → draft → review → promotion → WardrobeItem.
Хранить для предложенных значений происхождение, версию анализатора и уверенность;
подтверждённые человеком значения считать приоритетными. Полный ответ модели не хранить:
сохранить существующий принцип минимальной диагностики `ai_raw`.

Не выводить размер, состав ткани и бренд из внешнего сходства. Неизвестное оставлять пустым;
данные с бирки или страницы отделять от предположений по изображению.

Готово: подтверждённые цвет и сезон из фото реально попадают в каталог, передаваемый стилисту.

### 2. Обогатить уже загруженный гардероб

Сделать пакетный аудит: есть ли фото, категория, цвет, сезон, доступность;
показать список «нужно уточнить». Не требовать цену, бренд или точный состав для первого подбора.
Приоритет обработки: активные носимые вещи с отсутствующими базовыми атрибутами.

Распознавать исходное фото заново при необходимости; старые заметки не считать
надёжной структурированной разметкой. Предлагать заполнение пропусков, сохранять
ручные значения и показывать конфликт на подтверждение. Обработку вести небольшими
возобновляемыми пачками с предварительным подсчётом и отчётом изменений.

Ключ повторной обработки: вещь/фото, hash содержимого и версия анализатора.
Проверять версию карточки перед записью, чтобы не затереть одновременное редактирование.

Готово: повтор пакета не плодит вещи и не меняет подтверждённые поля молча.

### 3. Подготовить изображения

Сохранить исходник; из него создавать производные: нормализованное превью,
кроп вещи, затем при достаточном качестве вырез с прозрачным фоном.
Проверять ориентацию, формат, размер, резкость и попадание всей вещи в кадр.
Не менять цвет, принт, логотип и конструкцию генеративной дорисовкой.

Первый рабочий сценарий — одна вещь на фото с ручной коррекцией кропа.
При неудачном удалении фона оставить исходное превью и предложить переснять,
не блокируя уже пригодную карточку. Хранить производные с теми же правами доступа.

Для фотографий человека или нескольких вещей отдельным следующим этапом:
обнаружение объектов → bbox/маски → несколько предложенных карточек → выбор владельца
и подтверждение. Не создавать автоматически все объекты как принадлежащие пользователю.

Готово: изображения пригодны для коллажа, исходник сохранён, ошибки сегментации видны пользователю.

### 4. Дедупликация и проверка человеком

Сохранить существующий дедуп одинаковых файлов. Для разных ракурсов и сжатых копий
добавить подсказку «возможно, эта вещь уже есть» внутри доступного гардероба.
Пользователь выбирает: новое фото существующей вещи, новая вещь или пропуск.
Визуальное сходство не означает идентичность: две одинаковые футболки могут быть разными вещами.

Показывать исходное фото, предлагаемые атрибуты и сомнительные поля рядом.
Массовое подтверждение разрешать только для валидных карточек без нерешённых конфликтов;
низкая уверенность требует индивидуального просмотра.

Готово: фото одной вещи можно объединить вручную; автоматического удаления похожих вещей нет.

### 5. Готовность для стилиста и эксплуатация

Минимум для включения в подбор: подтверждённый владелец, существующий ID,
понятная категория/роль, подтверждённая карточка и допустимые текущие статусы.
Цвет и сезон повышают качество; неизвестные значения явно передаются как неизвестные.
Для погодозависимых ролей недостаток данных требует уточнения, а не уверенного совета.
Готовность вычислять по полям; отдельное хранимое состояние добавлять лишь при необходимости.

Сформировать текстовое представление из структурированных данных для плана 1.
Qdrant подключать только при доказанной необходимости визуального/семантического поиска;
источником прав и состояния вещи остаётся SQL. Если индекс появится — обязательный
scope владельца, проверка доступа до выдачи и удаление/переиндексация при изменениях.
Наличие Qdrant на риге само по себе не требует индексации гардероба.

## Модели и сервер

Сначала проверить vision-capabilities установленных моделей на риге и качество на
репрезентативных фото. Осмотр 2026-09-13 подтвердил Ollama и модели, но не vision-инференс.
Отдельно замерить распознавание, сегментацию, потребление RAM/VRAM и время на фото.
Модель удаления фона выбрать по этим замерам; две свободные CMP не считать готовым
вычислительным пулом без проверки поддержки. RAM сервера 7.6 GiB, свободный диск 43 GiB.

Переиспользовать очередь черновиков, claims и retry; не строить второй независимый
ingest-конвейер. Не держать HTTP-запрос загрузки до окончания AI-обработки.
Массовую обработку планировать вне времени ежедневных подборов; ограничить конкуренцию
на общем риге. Внешнюю обработку проводить в рамках разрешений профиля и бюджета.

## Приёмка и метрики

Набор пилота: 30–50 фотографий разных категорий, ракурсов и освещения, в том числе
размытые фото, дубли и несколько вещей на снимке. Отдельно — существующие карточки с ручными правками.

Обязательные проверки: передача атрибутов до prompt стилиста, сохранность ручных правок,
идемпотентность promotion, истечение lease, повтор обработки, удаление вещи во время
задачи, права семейных профилей и приватная выдача всех производных изображений.

Метрики: доля подтверждённых карточек с базовыми атрибутами, доля исправлений по каждому
полю, время на подтверждение вещи, ошибки/повторы, качество выреза, размер хранения
и доля вещей, реально участвующих в образах. Порог точности установить после разметки пилота;
обязательные инварианты — отсутствие потерь оригиналов, чужих данных и затирания ручных правок.

## Порядок небольших PR

1. Структурированные атрибуты от распознавания до подтверждённой карточки.
2. Аудит и безопасное обогащение существующих вещей.
3. Нормализация, кроп и производные изображения.
4. Подсказки дублей и review; затем многопредметные фото.
5. Пилот и измерения; индексирование только при подтверждённой потребности.

Общий порядок двух планов: этап 1 подготовки → ручной ежедневный подбор на пригодных
вещах → обогащение остального гардероба → расписание → улучшение изображений и дедуп.
