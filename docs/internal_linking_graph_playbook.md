# Граф внутренней перелинковки: эффект на WEARBASE и плейбук переноса

> Дата разбора: 2026-09-26. Данные: прод-БД (`brand_related`, `brand`, `yandex_*`),
> Mac-БД (`gsc_page_stats`, `gsc_index_status`), HTML-краул 2 780 активных карточек прода.
> Скрипты, которыми получены цифры, — [`scripts/linkgraph-audit/`](../scripts/linkgraph-audit/) (перезапускаемы).

## TL;DR

1. **Измеримого эффекта графа на индексацию и трафик WEARBASE не видно — и в текущем дизайне
   его нельзя было доказать.** Не было контрольной группы, пред-периода в GSC (9 дней) и журнала рёбер.
2. **Яндекс:** в поиске 2 769 из 2 780 активных карточек (99,6 %) при *любом* числе входящих; медиана
   «публикация → в поиске» ≤ 1 дня (точнее не видно: `first_seen_at` ставит ежедневный синк).
   Скорее всего это IndexNow-пинг в `publish-tick` + sitemap, а не граф (успешность пинга на проде
   отдельно не проверяли). Графу в Яндексе улучшать нечего.
3. **Google:** индексация определяется **возрастом страницы** (когорта июня ≈ 97 % в индексе, июля ≈ 60 %,
   августа ≈ 42 %) и **объёмом контента** (старые бренды с описанием ~450 симв. — 7–13 % в индексе
   даже при 12+ входящих). Внутри когорты градиента по числу входящих из графа нет
   (июль: 0 вх. → 63 %, 1–2 → 53 %, 3–5 → 63 %, 6–11 → 67 %, 12+ → 61 %).
   Внутри *недели* публикации разница 3+ входящих vs 0 = **+7 п.п.**, но крайне неоднородна (−27…+37) — не доказательство.
   Слабый сигнал есть и в **показах**: у брендов июля с 1–11 входящими средние показы за
   первые 30 дней 22–31 против 14 у брендов без входящих — но это корреляция, не доказательство (см. §2.4).
4. **Главная техническая находка — граф «богатые богатеют».** Фиксированный out-degree 12 + неизменяемые рёбра
   → ранние бренды заняли слоты друг другом, новичкам не достаётся доноров: **1 588 из 2 780 активных
   брендов (57 %) имеют 0 входящих рёбер графа**. Именно новые, ещё не известные Google страницы
   (у августовской когорты 50 % «URL is unknown to Google») сиротами и остались.
5. Для другого проекта: строить граф **сразу с рандомизированным holdout, журналом рёбер и
   резервом слотов под новичков** (§4–§5). Иначе через 3 месяца будет тот же ответ «не знаем».

### 2.3 Реальный граф из HTML (краул) vs `brand_related`

Краул 2026-09-26: 2 780/2 780 карточек ответили 200; на каждой 6–12 ссылок на другие бренды
(в среднем 9.4; меньше 6 — у 6 страниц). Входящие из HTML почти совпадают с таблицей:
**0 входящих — 1 574 бренда** (по `brand_related` 1 588), 1–2 — 289, 3–5 — 410, 6–11 — 228, 12+ — 279.
Фоллбек `findSimilarBrands` почти ничего не добавляет: у 99.8 % карточек граф и так даёт ≥ 6 ссылок.

Таблица «доза → отклик» по реальным входящим повторяет §2.2 с точностью до 1–3 п.п.
(июль: 63/55/62/65/61 % индексации; август: 42/42/52/34/61 %). Вывод не меняется.

### 2.4 Почему это корреляция, а не эффект

- **Отбор по близости.** Входящие достаются брендам, похожим на многих (частые стили, крупные города,
  богатый корпус для эмбеддингов). Эти же свойства сами по себе повышают показы. Контроля по «похожести» нет.
- **Отбор по времени.** Рёбра раздавались, пока у доноров были свободные слоты, — т.е. раньше публиковавшимся.
  Более ранние = более старые = лучше индексируются. Страты по месяцу гасят это лишь частично.
- **Мутируемое состояние.** `brand_related` хранит текущий граф; удалённые/заменённые рёбра не журналируются →
  граф «на дату X» не восстановить. Прод-граф ≠ Mac-граф (fill-пересборка не доехала).
- **Параллельные вмешательства** в те же недели: IndexNow, Google Indexing API (180 URL/день),
  контент-конвейер RAG, дрип, noindex не-ru локалей.

## 3. Технические особенности реализации (как сделано у нас)

**Таблица рёбер** (`migrations/Version20260612_brand_related.php`):
`brand_related(brand_id, related_brand_id, position, source, created_at)`,
`UNIQUE(brand_id, position)` + `UNIQUE(brand_id, related_brand_id)`, FK с каскадом на обе стороны.

**Построение** (`app:brand:build-link-graph`, `src/Service/BrandLinkGraphService.php`):
- Рёбра строятся **офлайн**, не на запрос → страница стабильна между обходами краулера.
- Источники по силе: `embedding` (Qdrant, top-K похожих по чанкам корпуса бренда; есть только в LAN,
  поэтому эмбеддинг-тир — в build-команде на Mac) > `style` (пересечение стилей) > `city`.
  Прод-сервис — чистый SQL (style/city), безопасен без Qdrant.
- OUT_DEGREE = 12 (кратно сетке 2/3/4 колонки — ровные ряды на всех брейкпоинтах).
- **Существующие рёбра неприкосновенны**; ребро заменяется только если target ушёл из `active`
  (`replaceDeadEdges`, обе стороны, в транзакции).
- `weave(brandId)` в `publish-tick`: новый бренд сразу получает исходящие + best-effort входящие
  (`ensureIncoming` — донор со свободным слотом). Fail-open: исключение глотается.
- Фильтр: не линкуем на `origin_status='foreign'`.
- Карточка (`BrandsController`): `findRelatedHard()` (только active-таргеты, порядок `position`);
  если меньше 6 — добивка `findSimilarBrands()` (стиль/город, `created_at DESC`).

**Грабли, которые мы собрали:**
1. **Fill-тир = ферма.** Добивка до out-degree произвольными брендами «чтобы не было сирот» давала
   нерелевантные ссылки (18 % рёбер). Убрали 07-19 — сирот стало больше, но это честнее.
2. **Богатые богатеют.** Неизменяемые рёбра + фиксированный out-degree → слоты доноров заполнены ранними
   брендами → новички без входящих. У нас 57 % активных — сироты графа. Лечение — §4 п.3.
3. **Dev ≠ прод.** Пересборку делали на Mac, прод остался со старым графом. Граф надо строить там,
   где его видит краулер, или синкать явно.
4. **Молчаливый fail-open.** `weave()` в `try/catch(\Throwable){}` — поломку вплетения никто не заметит.
   Нужен хотя бы лог/метрика «опубликован без входящих».
5. **Мерить по HTML, не по таблице.** Добивка `findSimilarBrands` в теории делает реальный граф ≠ `brand_related`.
   У нас разница оказалась мала (сирот 1 574 против 1 588), но проверить краулом обязательно:
   в другом проекте фоллбек может давать бо́льшую часть ссылок.
6. Баг-кандидат: в `findSimilarBrands` `orWhere('b.city = :city')` разрывает условия
   `status=active AND id != self` → в добивку может попасть неактивный бренд или сам бренд
   (в шаблоне фильтра нет). Не чинили в рамках разбора.

## 4. Плейбук для другого проекта

### 4.1 До изменения (обязательно, иначе эффект не измерить)
1. **Синк поисковых данных за 4+ недели до запуска.** GSC Search Analytics по страницам (дневной, с `page`),
   GSC URL Inspection по выборке, Яндекс.Вебмастер: история «страниц в поиске», показы/клики,
   список URL в поиске с датой первого появления. GSC API хранит 16 месяцев — сделать бэкфилл сразу.
2. **Снимок базовой линии** по каждой странице: coverage_state, первое появление в Яндексе, показы 28 дней.
3. **Выбрать метрики заранее** (§5) и записать гипотезу с порогом: «у treatment доля known в GSC через
   6 недель выше на ≥10 п.п.».

### 4.2 Построение графа
1. Таблица рёбер + **журнал рёбер** (`edge_log(src, dst, source, added_at, removed_at)` или
   append-only события) — чтобы граф на любую дату восстанавливался.
2. Кандидаты по релевантности: эмбеддинги контента > общие таксономии (стиль/категория) > гео.
   **Никакой добивки случайными страницами.** Out-degree переменный, 6–12 ссылок в видимом HTML-блоке
   (server-side рендер, `<a href>`, не JS).
3. **Резерв слотов под новичков:** например, 8 постоянных «релевантных» + 4 ротационных слота, которые
   отдаются страницам с in-degree < 2 (свежим), с ротацией раз в N недель. Либо входящие для нового узла
   берём у K самых похожих, вытесняя их *самое слабое* ребро (а не только при свободном слоте).
4. Стабильность: рёбра не пересчитываются на каждый запрос; меняются батчами и журналируются.
5. Строить граф **на проде** (или синкать его туда явно, с проверкой счётчиков).
6. Вплетение нового узла при публикации — с логированием результата (сколько входящих получил).

### 4.3 Рандомизированный holdout (самое важное)
- Случайные 20 % **новых** страниц (хеш от id, стратифицировать по категории) 6–8 недель **не получают
  входящих** из графа (исходящие — получают, чтобы не портить UX). Остальные 80 % — полное вплетение.
- Альтернатива дешевле — **ступенчатый запуск** (staggered rollout) по кластерам: кластер A включаем в
  неделю 0, B — в неделю 3, C — в неделю 6; сравнение diff-in-diff.
- После окна — включить граф для holdout и смотреть «догоняет ли» (второй естественный эксперимент).

## 5. Как мерить

### Метрики (в порядке чувствительности к внутренним ссылкам)
| Метрика | Источник | Почему |
|---|---|---|
| **Доля «URL is unknown to Google»** | GSC URL Inspection | Внутренние ссылки прежде всего влияют на *обнаружение*. Самая прямая метрика |
| Время «публикация → первый обход/индекс» | Inspection `lastCrawlTime`, Вебмастер first_seen | Скорость обнаружения |
| Доля в индексе (Submitted and indexed + с показами) | GSC Inspection | Итог |
| Показы/клики страницы за 28 дней после публикации | GSC Search Analytics по `page` | Трафик; самая шумная |
| Лог краулера: заходы Googlebot/YandexBot на страницу | nginx access log | Не зависит от квот API, самый быстрый сигнал |

⚠️ В Яндексе с IndexNow индексация почти мгновенная у всех — метрика индексации там не различает
группы, смотреть показы/позиции. Не-основные локали с `noindex` исключать из выборки.

### Анализ
1. **Основной:** treatment vs holdout по доле known/indexed и показам через 2/4/6/8 недель после публикации
   (χ² для долей, Mann-Whitney для показов — распределения с тяжёлым хвостом).
2. **Без holdout (как у нас):** «доза → отклик» по in-degree из **HTML-краула**, стратифицированно
