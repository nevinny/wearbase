# Ревью: подтверждение и одобрение владения брендом (BrandClaim)

Дата: 2026-10-04. Повод — заявка #16 на проде легла как `manual` без единого
доказательства владения, потому что штатного метода для неё не нашлось.

## Как устроено сейчас

`/brand-claim/{id}` показывает методы из `BrandClaimService::availableMethods()`:

| метод | условие доступности | что доказывает |
|---|---|---|
| `email_code` | у бренда заполнен `brand.email` | контроль почты бренда |
| `vk_admin` | есть vk-ссылка **и** `VkVerifier::isConfigured()` | админство в группе VK |
| `manual` | всегда | ничего, уходит админу |

Объявлены, но нигде не реализованы: `METHOD_DOCUMENT`, `METHOD_MARKETPLACE`.

При успехе self-serve метода `finishVerification()` либо сразу выдаёт владение
(`BRAND_CLAIM_AUTOGRANT_*=1`, админ получает только TG-уведомление), либо ставит
`email_verified` и ждёт админа. `manual` всегда уходит в `/admin/brand-claims`.

## Покрытие каталога (прод, 2781 опубликованный бренд)

| сигнал | брендов | доля |
|---|---|---|
| сайт (`brand_link.link_type='website'`) | 2004 | 72% |

## Находки

### 🔴 1. VK-метод мёртв на проде

`VK_APP_ID` пуст (`.env:64`, в `.env.local` не переопределён — подтверждено
`debug:dotenv`). `VkVerifier::isConfigured()` возвращает false → метод не попадает
в `availableMethods()` и не предлагается никогда. 688 брендов с vk-ссылкой лишены
автоматического пути. Код метода написан и работает — не хватает только credentials.

### 🔴 2. Админский approve не проверяет, есть ли у бренда другой владелец

`BrandClaimService::brandHasOtherOwner()` вызывается ровно в одном месте —
`BrandClaimController::finishVerification()` (self-serve ветка). Все три админских
пути (`BrandClaimController::approve`, `BrandClaimAdminController::approve`,
`BrandClaimDecideCommand::approve`) зовут `grantOwnership()` напрямую. Одобрение
второй заявки на тот же бренд молча создаёт второго owner'а с полными правами.

### 🔴 3. `reject` не проверяет текущий статус

Ни в одном из трёх мест. `approve` проверку имеет (`status IN (pending,
email_verified)`), `reject` — нет. Отклонение уже одобренной заявки переводит её в
`rejected`, но `BrandUser(owner)`, роли `ROLE_BRAND_*` и free-trial подписка,
созданные при approve, остаются. Права и журнал расходятся, и по журналу это
выглядит как «мы ему отказали».

### 🟠 4. Логика approve/reject размножена трижды

`BrandClaimController` (роуты `/brand-claim/admin/*`), `BrandClaimAdminController`
(роуты `/admin/brand-claims/*`) и `BrandClaimDecideCommand` — у последнего в
докблоке прямо написано «Точная реплика BrandClaimAdminController::approve()».
Копии уже разъехались: `setReviewedBy()` при отклонении ставит только
`BrandClaimController::reject()`, два других пути оставляют поле пустым.

### 🟠 5. Нет CSRF-защиты на админских approve/reject

Публичные POST-роуты проверяют `isCsrfTokenValid`, админские — нет, только
`IsGranted('ROLE_ADMIN')`.

### 🟡 6. Авто-выдача по email-коду опирается на адрес неизвестного происхождения

Все 858 брендов с email имеют `contact_status = NULL`, то есть адрес приехал из
импортов/RAG, а не от самого бренда. При `BRAND_CLAIM_AUTOGRANT_EMAIL=1` код
уходит на такой адрес и владение выдаётся без участия админа. Если адрес
принадлежит реселлеру или агрегатору — карточку заберёт он.

### 🟡 7. Заявка не знает о премодерации саморегов

Живой пример: заявка #16 на карточку 2804 и саморег-дубль 3681 от того же
человека. Анализатор премодерации сам пометил `duplicate_candidate:title~iseymordc`,
но `brand_claim` об этом ничего не знает, и админ видит две несвязанные записи в
двух разных интерфейсах.

## Предложения по автоматизации

Порядок — по отношению «покрытие / цена».

1. **Включить VK** — только credentials, кода писать не надо. 25% → 49% покрытия.
2. **Подтверждение по домену сайта** (DNS TXT `wearbase-verify=<код>` либо файл
   `/.well-known/wearbase-verify.txt`). Самый массовый сигнал — 2004 бренда, 72%.
   Проверка полностью автоматическая, доказательство сильное (контроль домена).
3. **Подтверждение через Telegram-канал**: выдаём код заявителю, он публикует пост
   в канале, мы читаем `https://t.me/s/<channel>` и ищем код. Канал публичный,
   API не нужен — этим приёмом мы уже читаем TG-каналы для RAG. +239 брендов и
   закрывает текущую заявку #16.
4. **Свести три копии approve/reject в один метод сервиса** с проверками статуса и
   второго владельца. Без этого любая новая автоматизация будет множить
   расхождения из находок 2–4.
5. **Переиспользовать скоринг премодерации для claim.** В `brand_moderation` уже
   есть `verdict` / `identity_match` / `control_proof` / `red_flags`, и анализатор
   умеет их считать. Прогонять через него и заявки — тогда админ видит готовый
   вердикт, а не сырой комментарий заявителя, а часть заявок закрывается без него.
6. **Связать claim с саморег-дублями** того же пользователя (анализатор уже
   находит их) и дать в админке одно действие «одобрить заявку + схлопнуть дубль».

Пункты 1–3 поднимают автоматическое покрытие с 31% до ~82% каталога. Пункт 4 —
предварительное условие, чтобы это не разъехалось.
